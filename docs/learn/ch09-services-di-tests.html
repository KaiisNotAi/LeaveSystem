1. 先製造問題：把規則塞進 Controller

假設現在要做「送出請假申請」。使用者填了起訖時間，你要算出實際時數。 最直覺的做法是直接寫在 Controller 裡：

C#❌ 先看看不該怎麼寫
[HttpPost]
public async Task<IActionResult> Create(LeaveRequestCreateViewModel input)
{
    if (!ModelState.IsValid) return View(input);

    // ── 時數計算就這樣塞進來 ──
    var startAt = input.StartDate.Date.AddHours(input.StartHour);
    var endAt   = input.EndDate.Date.AddHours(input.EndHour);

    decimal total = 0m;
    for (var day = startAt.Date; day <= endAt.Date; day = day.AddDays(1))
    {
        // 上午 08:00~12:00 的重疊
        var mStart = day.AddHours(8) > startAt ? day.AddHours(8) : startAt;
        var mEnd   = day.AddHours(12) < endAt  ? day.AddHours(12) : endAt;
        if (mEnd > mStart) total += (decimal)(mEnd - mStart).TotalHours;

        // 下午 13:00~17:00 的重疊…（再來一遍）
    }

    // …然後才是真正存檔…
}
這樣寫會遇到什麼

① 沒辦法測試。你想確認「11:00–14:00 應該算 2 小時」， 但這段邏輯困在一個需要 HTTP 請求、需要資料庫、需要登入的方法裡。 你只能開瀏覽器一次一次手動試。

② 沒辦法重複使用。第 12 章的匯出報表也要算時數， 你只能複製貼上一份——然後其中一份改了另一份沒改。

③ Controller 會長到 400 行。時數、上限檢查、簽核規則展開、 通知……全部塞進來之後，沒有人看得懂它在幹嘛。

2. 請假時數規則

先把規則講清楚（寫程式前先把規格寫成人話，這是好習慣）：

#規則
1上課時段是 08:00–12:00 與 13:00–17:00
2午休 12:00–13:00 不計時數
3可以跨日，逐日計算與上課時段的重疊
4起訖必須是整點，且介於 08:00–17:00
5結束必須晚於開始
6完全沒碰到上課時段（例如只選午休）＝ 無效申請

幾個例子，等一下要拿來當測試案例：

3. 抽成 Service

照第 1 章第 7 節的做法：先訂介面，再寫實作。

新增檔案Services/ILeaveCalculator.cs
namespace MyLeaveSystem.Services;

public interface ILeaveCalculator
{
    /// <summary>
    /// 計算請假時數。
    /// 成功回 true 並填入 totalHours；失敗回 false 並填入 errorMessage。
    /// </summary>
    bool TryCalculate(DateTime startAt, DateTime endAt,
                      out decimal totalHours, out string? errorMessage);
}
新增檔案Services/LeaveCalculator.cs
namespace MyLeaveSystem.Services;

/// <summary>
/// 請假時數計算。上課時段 08:00~12:00、13:00~17:00，午休不計，可跨日。
/// </summary>
public class LeaveCalculator : ILeaveCalculator
{
    public bool TryCalculate(DateTime startAt, DateTime endAt,
                            out decimal totalHours, out string? errorMessage)
    {
        totalHours = 0m;
        errorMessage = null;

        // 規則 4：必須是整點
        if (!IsOnTheHour(startAt) || !IsOnTheHour(endAt))
        {
            errorMessage = "請假時間必須使用整點（例如 08:00、13:00）。";
            return false;
        }

        // 規則 5
        if (endAt <= startAt)
        {
            errorMessage = "結束時間必須晚於開始時間。";
            return false;
        }

        // 規則 4：伺服器端也要擋，不能只靠前端下拉選單
        if (!IsSelectableHour(startAt.Hour) || !IsSelectableHour(endAt.Hour))
        {
            errorMessage = "請假時間需介於每日 08:00 到 17:00 的整點時段。";
            return false;
        }

        var range = (Start: startAt, End: endAt);

        // 規則 1~3：逐日算與兩個上課區段的重疊
        for (var day = startAt.Date; day <= endAt.Date; day = day.AddDays(1))
        {
            totalHours += OverlapHours(range, (day.AddHours(8),  day.AddHours(12)));
            totalHours += OverlapHours(range, (day.AddHours(13), day.AddHours(17)));
        }

        // 規則 6
        if (totalHours <= 0)
        {
            errorMessage = "請假區間未涵蓋任何上課時段，請重新選擇。";
            return false;
        }

        return true;
    }

    private static bool IsOnTheHour(DateTime dt)
        => dt.Minute == 0 && dt.Second == 0 && dt.Millisecond == 0;

    private static bool IsSelectableHour(int hour) => hour >= 8 && hour <= 17;

    // 兩個時間區間的交集有幾小時（沒交集回 0）
    private static decimal OverlapHours((DateTime Start, DateTime End) a,
                                          (DateTime Start, DateTime End) b)
    {
        var start = a.Start > b.Start ? a.Start : b.Start;   // 兩個開始取晚的
        var end   = a.End   < b.End   ? a.End   : b.End;     // 兩個結束取早的

        return end <= start ? 0m : (decimal)(end - start).TotalHours;
    }
}
看這個類別最重要的一件事：它什麼都不依賴

沒有 AppDbContext、沒有 HttpContext、沒有檔案、沒有網路。 純輸入 → 純輸出。

這種類別叫「純函式」，是最容易測試的東西—— 不用準備資料庫、不用模擬 HTTP 請求，直接呼叫就好。第 5 節你馬上會看到差別有多大。

所以抽 Service 時有個原則：優先把「純計算」的部分抽出來， 它的投資報酬率最高。

4. 依賴注入與三種生命週期

4.1 登記

修改Program.cs
using MyLeaveSystem.Services;

builder.Services.AddDbContext<AppDbContext>(/* … */);

builder.Services.AddScoped<ILeaveCalculator, LeaveCalculator>();

這一行的意思是：「誰要 ILeaveCalculator，就給他一個 LeaveCalculator。」

4.2 使用

C#Controller 只要在建構式「要求」
public class LeaveRequestsController : Controller
{
    private readonly AppDbContext _db;
    private readonly ILeaveCalculator _calculator;

    // 你不用自己 new，框架會把東西塞進來
    public LeaveRequestsController(AppDbContext db, ILeaveCalculator calculator)
    {
        _db = db;
        _calculator = calculator;
    }

    [HttpPost]
    public async Task<IActionResult> Create(LeaveRequestCreateViewModel input)
    {
        var startAt = input.StartDate.Date.AddHours(input.StartHour);
        var endAt   = input.EndDate.Date.AddHours(input.EndHour);

        // 原本 20 行的計算，變成一行
        if (!_calculator.TryCalculate(startAt, endAt, out var hours, out var error))
        {
            ModelState.AddModelError(string.Empty, error!);
            return View(input);
        }

        // …存檔…
    }
}
為什麼要這麼麻煩？直接 new LeaveCalculator() 不行嗎？

單看這個例子，new 一個確實比較短。差別在換掉它的時候：

① 換實作不用改 Controller。 假設之後上課時段要改成可設定的（存在資料庫裡）， 你寫一個 ConfigurableLeaveCalculator， 只改 Program.cs 那一行登記， 所有用到的地方自動換掉。

② 測試可以塞假的。測 Controller 時， 你可以塞一個「永遠回傳 8 小時」的假計算器， 專心測 Controller 自己的邏輯。

③ 相依物件的相依物件也自動處理。 LeaveCalculator 如果自己也需要別的東西，DI 會一路組好給你。 自己 new 的話就要手動一層一層建。

4.3 三種生命週期

方法多久建一個新的什麼時候用
AddScoped 每個 HTTP 請求一個 預設就用這個。只要間接用到 AppDbContext 就必須是它。
AddTransient 每次要求都新建一個 很輕量、不保存狀態的小工具。
AddSingleton 整個程式只有一個，
所有請求共用		 設定值、快取。要自己處理多執行緒安全。
最危險的錯誤：Singleton 抓住 Scoped

如果你把一個用到 AppDbContext 的 Service 註冊成 AddSingleton， 它會永遠抓著第一個請求的那個 DbContext。

結果是：多個使用者共用同一個變更追蹤狀態、連線超時、 A second operation was started on this context… 之類的隨機錯誤。 而且只有在多人同時用的時候才會出現，本機測試永遠測不到。

記住規則：不確定就用 AddScoped。 完成品專案的 11 個服務全部都是 Scoped。

5. 寫第一個測試

現在來證明時數算得對。建立測試專案：

終端機在 MyLeaveSystem 的「上一層」資料夾
dotnet new xunit -o MyLeaveSystem.Tests
cd MyLeaveSystem.Tests
dotnet add reference ../MyLeaveSystem/MyLeaveSystem.csproj
為什麼測試要獨立一個專案 測試程式碼不該被部署到正式環境。獨立專案就能確保它不會被打包進去， 而且測試專案可以裝一些正式專案用不到的套件。
新增檔案MyLeaveSystem.Tests/LeaveCalculatorTests.cs
using MyLeaveSystem.Services;
using Xunit;

namespace MyLeaveSystem.Tests;

public class LeaveCalculatorTests
{
    private readonly ILeaveCalculator _sut = new LeaveCalculator();
    // sut = System Under Test（被測試的東西），是常見的命名慣例

    [Fact]   // [Fact] = 一個沒有參數的測試
    public void 整個上午_應該是4小時()
    {
        // Arrange（準備）
        var start = new DateTime(2026, 6, 9, 8, 0, 0);
        var end   = new DateTime(2026, 6, 9, 12, 0, 0);

        // Act（執行）
        var ok = _sut.TryCalculate(start, end, out var hours, out var error);

        // Assert（驗證）
        Assert.True(ok);
        Assert.Equal(4m, hours);
        Assert.Null(error);
    }

    [Fact]
    public void 跨越午休_午休不計時數()
    {
        var start = new DateTime(2026, 6, 9, 11, 0, 0);
        var end   = new DateTime(2026, 6, 9, 14, 0, 0);

        var ok = _sut.TryCalculate(start, end, out var hours, out _);

        Assert.True(ok);
        Assert.Equal(2m, hours);     // 不是 3！這就是這條規則的重點
    }

    [Fact]
    public void 只選午休_應該失敗()
    {
        var start = new DateTime(2026, 6, 9, 12, 0, 0);
        var end   = new DateTime(2026, 6, 9, 13, 0, 0);

        var ok = _sut.TryCalculate(start, end, out var hours, out var error);

        Assert.False(ok);
        Assert.Equal(0m, hours);
        Assert.NotNull(error);
    }

    // [Theory] = 同一段測試邏輯，跑多組資料
    [Theory]
    [InlineData(8, 17, 8)]      // 整天 → 8 小時
    [InlineData(8, 12, 4)]      // 上午 → 4 小時
    [InlineData(13, 17, 4)]     // 下午 → 4 小時
    [InlineData(11, 14, 2)]     // 跨午休 → 2 小時
    [InlineData(8, 9, 1)]       // 一小時
    public void 同日各種區間(int startHour, int endHour, decimal expected)
    {
        var start = new DateTime(2026, 6, 9, startHour, 0, 0);
        var end   = new DateTime(2026, 6, 9, endHour, 0, 0);

        var ok = _sut.TryCalculate(start, end, out var hours, out _);

        Assert.True(ok);
        Assert.Equal(expected, hours);
    }

    [Fact]
    public void 跨日_第一天下午加第二天上午()
    {
        var start = new DateTime(2026, 6, 9, 13, 0, 0);
        var end   = new DateTime(2026, 6, 10, 12, 0, 0);

        var ok = _sut.TryCalculate(start, end, out var hours, out _);

        Assert.True(ok);
        Assert.Equal(8m, hours);     // 4 + 4
    }

    [Fact]
    public void 非整點_應該失敗()
    {
        var start = new DateTime(2026, 6, 9, 8, 30, 0);
        var end   = new DateTime(2026, 6, 9, 12, 0, 0);

        Assert.False(_sut.TryCalculate(start, end, out _, out var error));
        Assert.Contains("整點", error);
    }
}

感受一下差別

這九個測試在不到一秒內跑完， 而且不需要資料庫、不需要瀏覽器、不需要登入。

如果這段邏輯還留在 Controller 裡，你要驗證這九種情況， 得手動開瀏覽器、登入、填表單、送出、看結果——九遍。 而且每次改程式都要再來一遍。

這就是抽 Service 最直接的回報。

5.1 測試的三段式結構

段落做什麼
Arrange 準備準備輸入資料、建立被測物件
Act 執行呼叫要測的那個方法。通常只有一行
Assert 驗證檢查結果對不對
測試名稱用中文沒關係 C# 允許中文識別字。測試名稱的目的是「失敗時一眼看出壞了什麼」， 用中文反而更清楚。完成品專案的測試也是這樣命名的。

5.2 動手：故意弄壞它

把 LeaveCalculator 裡下午時段的 13 改成 12：

C#故意改壞
totalHours += OverlapHours(range, (day.AddHours(12), day.AddHours(17)));   // 原本是 13

再跑 dotnet test：

輸出終端機
失敗 跨越午休_午休不計時數 [2 ms]

它精準地告訴你哪條規則壞了、預期多少、實際多少。 改回 13，再跑一次，全綠。這就是測試在做的事。

6. TDD 的節奏

剛才是「先寫程式再補測試」。反過來做叫 TDD（測試驅動開發）：

  1. 紅：先寫一個會失敗的測試（因為功能還不存在）
  2. 綠：寫最少的程式碼讓它通過
  3. 重構：在測試保護下把程式碼整理乾淨
TDD 適合什麼、不適合什麼

很適合：規則明確、輸入輸出清楚的東西。 時數計算、簽核權限判斷、日期正規化——這些先寫測試非常順。

不太適合：畫面長什麼樣、版面好不好看。 那些用眼睛看比較快。

完成品專案就是這樣分的： Services/ 底下的邏輯有 106 個測試， Controller 與 View 則靠手動驗收清單。不是所有東西都值得寫測試。

7. 分層的完整樣貌

到這裡，你的專案已經有完整的分層了：

瀏覽器 │ HTTP 請求 ▼ Controller 收 → 轉 → 給 │ ‧ 接參數、驗證 ModelState │ ‧ 決定回哪個 View / 轉去哪 │ ‧ 不算業務規則 ▼ Service 業務規則 │ ‧ 時數怎麼算、能不能簽、超過上限沒 │ ‧ 回傳「結果物件」而不是 IActionResult │ ‧ 不碰 HttpContext ▼ AppDbContext（EF Core） 資料存取 │ ▼ SQL Server

每一層都有一條「不做什麼」的規則，那才是分層的重點：

這一層該做不該做
Controller 接參數、呼叫 Service、選畫面 不寫業務規則（不然沒辦法測）
Service 業務規則、回傳結果物件 不碰 HttpContext、不回 IActionResult （不然又綁死在 Web 上）
Entity 描述資料長什麼樣 不放跟畫面有關的東西（那是 ViewModel 的事）
Service 該回傳什麼

不要回 IActionResult（那是 Web 專屬的），也盡量不要用丟例外表達「使用者做錯了」。 用一個小小的結果物件最好用：

public record ApprovalActionResult(bool Success, string? ErrorMessage, ApprovalOutcome Outcome);

Controller 拿到之後自己決定要怎麼呈現。 完成品專案的 ApprovalService 與 AbsenceRecordService 都是這個體例。
