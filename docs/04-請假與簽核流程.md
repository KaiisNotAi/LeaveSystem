# 04 — 請假與簽核流程

## 0. 目前實作狀態（Phase 4）

> 本文件描述完整目標流程；以下是目前程式碼已完成範圍（`feature/phase4-approval-engine`）：

- ✅ 學員可送出請假申請（送出即 `Pending`）
- ✅ `LeaveCalculator` 已實作（整點、跨午休、跨日）
- ✅ 送出前班期上限檢查（`Approved` 累計 + 本次）
- ✅ 送出時依 `ApprovalRule` 建立 `LeaveRequestStep`（全部 `Pending`）
- ✅ 導師/科長/分署長待辦頁（`/Approvals`）已實作
- ✅ 單關核准邏輯已實作（有下一關推進 `CurrentLevel`；最後一關改 `LeaveRequest.Status=Approved`）
- ✅ 單關駁回邏輯已實作（`Comment` 必填；整張改 `LeaveRequest.Status=Rejected`）
- ✅ 關卡與身分驗證已實作（必須是 `CurrentLevel` 且為該班期該角色指定簽核人）
- ✅ 重複簽核防護已實作（同一 Step 不能重複簽）

## 1. LeaveRequest 狀態機

```
	   建立草稿
		   │
		   ▼
	  ┌────────┐    送出      ┌──────────┐
	  │ Draft  │─────────────→│ Pending  │
	  └────────┘              │（簽核中）│
							  └────┬─────┘
								   │
			  ┌────────────────────┼────────────────────┐
			  │                    │                    │
			  ▼                    ▼                    ▼
		 ┌────────┐         ┌──────────┐         ┌────────────┐
		 │Approved│         │ Rejected │         │ Cancelled  │
		 │(全核准)│         │(任一駁回)│         │(學員撤銷)  │
		 └────────┘         └──────────┘         └────────────┘
```

## 2. 簽核派送邏輯（ApprovalRouter）

當學員按下「送出」時：

```
1. 計算請假總時數 totalHours = LeaveCalculator.Calculate(StartAt, EndAt)

2. 查 ApprovalRule，找到第一筆滿足：
   MinHours <= totalHours AND (MaxHours IS NULL OR totalHours <= MaxHours)

3. 從規則的 RequiredRoles JSON 解析出角色清單：
   ["Tutor"] / ["Tutor","SectionChief"] / ["Tutor","SectionChief","BranchDirector"]

4. 為每個角色建立一筆 LeaveRequestStep：
   Level = 1, 2, 3...
   ApproverRole = 角色字串
   Decision = Pending

5. 設定 LeaveRequest:
   Status = Pending
   CurrentLevel = 1
```

## 3. 單關簽核處理

當第 N 關簽核人點「核准」或「駁回」：

### 3.1 核准

```
更新此 Step:
   Decision = Approved
   ApproverUserId = 當前使用者
   Comment = 意見
   DecidedAt = 現在

判斷是否還有下一關：
   IF 還有 Step.Level > CurrentLevel
	   LeaveRequest.CurrentLevel++
	   通知下一關簽核人
   ELSE
	   LeaveRequest.Status = Approved
	   通知申請人「已核准」
```

### 3.2 駁回

```
更新此 Step:
   Decision = Rejected
   ApproverUserId = 當前使用者
   Comment = 駁回原因（必填）
   DecidedAt = 現在

LeaveRequest.Status = Rejected
通知申請人「被駁回」+ 原因
（後續關卡的 Step 保持 Pending，不再處理）
```

## 4. 誰能看到誰的待辦？

| 角色 | 看得到的待辦 |
|------|-------------|
| 導師 | 班期所屬學員、CurrentLevel=1 且該關 Role=Tutor 的單 |
| 科長 | 班期所屬、CurrentLevel=2 且該關 Role=SectionChief 的單 |
| 分署長 | 同上但 Role=BranchDirector |

關鍵：**Level 必須等於 CurrentLevel**，否則前一關還沒簽，下一關不會看到。

## 5. 班期請假上限檢查

學員送出申請前：

```
1. 從 Cohort 取出 LeaveLimitHours
2. 累計該學員此班期所有 Status=Approved 的 LeaveRequest.TotalHours
3. 加上本次申請的 totalHours
4. IF 累計 > LeaveLimitHours
	   拒絕送出，顯示「將超過班期請假上限 X 小時」
```

## 6. 時數計算規則（LeaveCalculator）

每日上課時段：
- 上午：08:00 ~ 12:00（4 小時）
- 下午：13:00 ~ 17:00（4 小時）
- 午休 12:00 ~ 13:00 不計

### 範例

| 區間 | 計算 |
|------|------|
| 6/9 08:00 ~ 6/9 09:00 | 1 小時 |
| 6/9 11:00 ~ 6/9 14:00 | 1（11-12）+ 1（13-14）= 2 小時 |
| 6/9 08:00 ~ 6/9 17:00 | 4 + 4 = 8 小時（一整天） |
| 6/9 08:00 ~ 6/10 17:00 | 8 + 8 = 16 小時 |
| 6/9 13:00 ~ 6/10 12:00 | 4 + 4 = 8 小時 |

最小單位 1 小時，學員下拉選單只能選整點時間。

## 7. 紀錄查詢與時數統計（Phase 5）

Phase 5 提供純查詢功能，不影響任何簽核狀態，也不寫回資料庫。

### 7.1 學員紀錄查詢（`/Reports/Index`）

學員可依下列欄位（皆選填）篩選**自己**的請假紀錄：

| 篩選欄位 | 對應 LINQ 條件 |
|------|------|
| 狀態 `Status` | `r.Status == Status` |
| 假別 `LeaveTypeId` | `r.LeaveTypeId == LeaveTypeId` |
| 日期起 `DateFrom` | `r.StartAt >= DateFrom` |
| 日期迄 `DateTo` | `r.StartAt <= DateTo` |

- 一律以「學員自己的 `UserId`」為 WHERE 主條件，不接受任意 UserId 越權查詢。
- 未填的欄位視為「不限」，實作上以 `if (query.Xxx.HasValue)` 動態串接。
- 預設排序：`CreatedAt DESC`（最新在最上面）。

### 7.2 學員累計時數統計（`/Reports/Summary`）

- **狀態口徑**：**只累計 `LeaveStatus.Approved`** 的請假單。
  - 與 `LeaveRequestsController.Create` 送單時的班期上限檢查完全一致，避免規則分歧。
  - `Pending`、`Rejected`、`Cancelled` 不計入。
- 顯示內容：
  1. 各假別累計時數與筆數（表格或卡片形式）。
  2. 班期上限進度條：已核准 X 小時 / 上限 Y 小時（Y = `Cohort.LeaveLimitHours`）。
- 若學員尚未指派班期（`CohortId=null`），只顯示已核准時數，隱藏上限進度條並提示「尚未指派班期」。

### 7.3 行政彙總報表（`/Reports/Admin`）

僅 `Admin` / `Staff` 可存取。

- **分組維度**：`Cohort × Student × LeaveType × YearMonth`（四層 GroupBy Key）。
- **統計欄位**：`TotalHours`（時數合計）、`RequestCount`（筆數）。
- **狀態口徑**：與 §7.2 一致，**只算 `LeaveStatus.Approved`**。
- **月份切法**：依 `StartAt.Year` / `StartAt.Month`；跨月請假**整筆算開始月**。
  - 例：`6/28 08:00 ~ 7/2 17:00` 的一筆 20 小時單，全部歸入 6 月（**不**拆分）。
  - 選這條規則的原因：測試好寫、與人工判讀一致；若日後要精確分攤再開新 Phase 處理。
- **篩選條件（皆選填）**：
  - `CohortId`：班期
  - `StudentId`：學員（可能會依所選班期動態縮小；MVP 先做獨立下拉）
  - `LeaveTypeId`：假別
  - `DateFrom` / `DateTo`：日期起迄，以 `StartAt` 為比對欄位。使用標準 `<input type="date">` 提供日期選擇器；若 `DateTo` 只帶到日期（時間為 00:00:00），Service 會補到當日 `23:59:59` 以「含當天」為語意。注意：**篩選粒度到天，但彙總維度仍然是「年月」**（跨月整筆算開始月），篩選日期只決定「哪些請假單被納入計算」，不影響群組切法。
- 預設排序：Cohort → Student → LeaveType → Year → Month（穩定可預期，測試好斷言）。

### 7.4 權限規則

| 頁面 | 允許角色 | 授權標記 |
|------|------|------|
| `/Reports/Index` | Student | `[Authorize(Roles="Student")]` |
| `/Reports/Summary` | Student | `[Authorize(Roles="Student")]` |
| `/Reports/Admin` | Admin, Staff | `[Authorize(Roles="Admin,Staff")]` |

- 學員嘗試訪問 `/Reports/Admin` 應被 Cookie 認證中介軟體導向 `/Account/AccessDenied`。
- 服務層 `GetMyRequestsAsync` / `GetMyLeaveTypeSummaryAsync` 均以傳入的 `studentId` 為 WHERE 條件，避免 Controller 若誤傳可越權讀他人資料。

## 8. 曠課紀錄（Phase 6）

Phase 6 補上「曠課」這條與請假**並行但獨立**的資料流；曠課是行政事後登錄的既定事實，**不走簽核流程**，也不會影響請假單的 `LeaveStatus`。設計理由與規格詳見 `docs/01 §3.5` 與 `Models/Entities/AbsenceRecord.cs`。

### 8.1 資料模型與稽核欄位

| 欄位 | 型別 / 限制 | 說明 |
|------|-------------|------|
| `Id` | int (PK) | 自動編號 |
| `StudentId` | int FK→`UserAccount` | 學員；Service 會強制驗證該 Id 擁有 `Student` 角色 |
| `OccurredAt` | datetime | 曠課發生時間（含日期與上課時段起點） |
| `Hours` | decimal(6,2)，`[Range(1, 100)]` | 曠課時數；同時受 ViewModel 的整數規則約束 |
| `Note` | nvarchar(500)? | 備註；全空白會被 Service 存成 `null` |
| `CreatedByUserId` | int FK→`UserAccount` | 登錄者（行政），**Update 時不覆寫** |
| `CreatedAt` | datetime | 建立時間，**Update 時不覆寫**；Create 時一律以 `DateTime.UtcNow` 寫入 |

- 稽核欄位在 `AbsenceRecordService.UpdateAsync` 中被刻意保留，以維持「誰、什麼時候第一次登錄」的可追溯性。

### 8.2 業務規則

1. **只有 Admin / Staff 可 CRUD**：`/Admin/AbsenceRecords/*` 以 `[Authorize(Roles = "Admin,Staff")]` 保護。
2. **學員只能查閱自己的紀錄**：`/AbsenceRecords` 以 `[Authorize(Roles = "Student")]` 保護，且 Service 以「登入者 UserId」為 WHERE 主條件，即使前端偽造 URL 也讀不到他人資料。
3. **StudentId 必為 Student 角色**：`AbsenceRecordService.CheckStudentAsync` 檢查 `UserRoles` 內含 `Student`；任何指向非 Student 的 UserId 都會被 `CreateAsync` / `UpdateAsync` 拒絕。
4. **StudentId 必已指派班期**（Phase 6 UX 優化補強）：同上檢查會回一個「找到但 `CohortId is null`」的失敗訊息。此規則有兩層防線：
    - UI 層：`GetStudentOptionsAsync` 直接把未歸班的學員從下拉排除，讓行政連選都選不到。
    - Service 層：即使被偽造 POST，`CreateAsync` / `UpdateAsync` 仍會擋下並回專屬錯誤訊息。
5. **不與請假單耦合**：`AbsenceRecord` 沒有 `LeaveRequestId` FK；同一天同時存在「已核准請假」與「曠課紀錄」是允許的（例如上午請假下午未到）。

### 8.3 時數與驗證規則

- Entity：`[Range(1, 100)]` 擋掉 0、負數、超過 100 小時的離譜輸入。
- ViewModel（`AbsenceRecordCreateInput` / `AbsenceRecordEditInput`）：
  - `[Required]` + `[Range(1, 100, ...)]` 提供友善錯誤訊息。
  - `IValidatableObject.Validate` 額外檢查「必須為整數」：`Hours != Math.Floor(Hours)` 即回錯誤，用以擋 1.5 這種小數（`[Range]` 擋不掉）。
- Service `NormalizeNote`：`null` / 全空白 → `null`，否則 `Trim()` 後寫入，避免資料庫存下大量看不見的空白。

### 8.3.1 兩層下拉 UX（Create / Edit）

新增與編輯表單採「班期 → 學員」兩層下拉，避免學員多的時候一個下拉幾百筆難用：

- 「班期」是**純前端 UX 欄位**（無 `asp-for`、無 `name`），不會被 Model Binding。
- 每個學員 `<option>` 掛 `data-cohort-id`；一段小型 vanilla JS 依所選班期即時 `hidden` 掉不同班的 option。
- Edit 頁面進場時會**讀取目前 StudentId 對應 option 的 `data-cohort-id`** 反推設定班期下拉，讓行政一進來就看到「已過濾成該班學員」的視圖。
- JS 若失效，學員下拉會退化為顯示全部（因為都是 `<option>`），資料仍完整；且業務規則由 Service 把關，不會因前端漏擋而讓髒資料進資料庫。

### 8.4 日期篩選語意

- 兩個查詢頁（行政 `/Admin/AbsenceRecords`、學員 `/AbsenceRecords`）都以 `<input type="date">` 收 `DateFrom` / `DateTo`，比對欄位一律是 `AbsenceRecord.OccurredAt`。
- Service `NormalizeDateTo`：若 `DateTo` 時間為 `00:00:00`，會補到當日 `23:59:59.9999999` 以「含當天」為語意（體例對齊 Phase 5 `AdminReportQuery.DateTo`）。
- 行政 `AbsenceRecordAdminViewModel.TotalHours` = **目前篩選結果**的加總，會隨條件變化。
- 學員 `MyAbsenceRecordViewModel.TotalHours` = **該學員終身總曠課時數**，**刻意不受日期篩選影響**；設計目的是讓學員每次進頁面都看到一個穩定的自我警惕數字。

### 8.5 權限與路由對照

| 路徑 | 動作 | 允許角色 | 授權標記 |
|------|------|---------|---------|
| `/AbsenceRecords` (GET) | 學員自查列表 | Student | `[Authorize(Roles="Student")]` |
| `/Admin/AbsenceRecords` (GET) | 行政列表 + 篩選 | Admin, Staff | `[Authorize(Roles="Admin,Staff")]` |
| `/Admin/AbsenceRecords/Create` (GET/POST) | 新增曠課 | Admin, Staff | 同上 |
| `/Admin/AbsenceRecords/Edit/{id}` (GET/POST) | 編輯曠課 | Admin, Staff | 同上 |
| `/Admin/AbsenceRecords/Delete/{id}` (POST) | 刪除曠課 | Admin, Staff | 同上 |

- 學員嘗試訪問 `/Admin/AbsenceRecords*` 應被 Cookie 認證中介軟體導向 `/Account/AccessDenied`。
- 行政或其他非 Student 角色訪問 `/AbsenceRecords` 也會被拒（避免「行政以自己身分自查」造成誤解）。

### 8.6 兩個同名 Controller 的 View 路徑分流

Phase 6 同時存在兩個 `AbsenceRecordsController`：

- `Controllers/AbsenceRecordsController.cs` → 學員自查（`/AbsenceRecords`）
- `Controllers/Admin/AbsenceRecordsController.cs` → 行政 CRUD（`/Admin/AbsenceRecords/*`）

因為 `Program.cs` 為了行政後台把 `/Views/Admin/{1}/{0}.cshtml` **插入到 `ViewLocationFormats` 最前面**（讓 `Controllers/Admin/XxxController` 的 View 可以擺在 `Views/Admin/Xxx/`），這也讓學員版的預設 view 尋找會**先命中** `Views/Admin/AbsenceRecords/Index.cshtml`，而該檔期望的模型型別是 `AbsenceRecordAdminViewModel`，跟學員頁的 `MyAbsenceRecordViewModel` 不符，直接執行會拋出型別轉換錯誤。

因此學員版 Controller 用**絕對路徑**顯式指定 View：

```csharp
return View("~/Views/AbsenceRecords/Index.cshtml", vm);
```

未來若再遇到「同名 Controller、一個在 `Admin/`、一個在根」的情況，記得沿用這種絕對路徑寫法，或另外新增 View 搜尋規則。
