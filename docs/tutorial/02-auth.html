Flow 02 · Authentication

登入認證與 Cookie

「登入」這件事在程式裡其實是兩個獨立動作： 驗證（你是不是你）由 AuthService.ValidateAsync 負責， 簽入（把身分寫成 Cookie）由 AuthService.SignInAsync 負責。 之後每個請求的 [Authorize(Roles = "Staff,Admin")]， 比對的都是這裡寫進 Cookie 的 ClaimTypes.Role。

瀏覽器 中介軟體 Controller Service EF Core 資料庫

程式碼對照

1 POST /Account/Login Views/Account/Login.cshtml

表單用 asp-action="Login" 送出，欄位名對應 LoginViewModel 的 Username / Password / RememberMe。 Tag Helper 會自動夾帶一個隱藏的防偽權杖欄位。 

<form method="post" asp-action="Login" asp-route-returnUrl="@Model.ReturnUrl">
    <input asp-for="Username" class="form-control" autocomplete="username" autofocus />
    <input asp-for="Password" class="form-control" autocomplete="current-password" />
</form>
2 [HttpPost] [ValidateAntiForgeryToken] Login(LoginViewModel input) AccountController.cs:42–44

路由把請求交給這個 Action 之前，管線已經做完兩件事： 把表單欄位模型繫結成 LoginViewModel， 以及驗證防偽權杖（擋 CSRF：別的網站沒辦法偽造這個一次性 token）。 

[HttpPost]
[ValidateAntiForgeryToken] // 防止 CSRF 攻擊
public async Task<IActionResult> Login(LoginViewModel input)
3 if (!ModelState.IsValid) return View(input); AccountController.cs:46–50（回傳於 :49）

第一道檢查只看欄位本身（[Required] 等資料註解）， 還沒碰到資料庫。這裡就擋掉，可以少一次無謂的查詢。 

// 步驟 1：先檢查表單欄位本身有沒有缺漏（[Required] 等）
if (!ModelState.IsValid)
{
    return View(input);
}
4 _authService.ValidateAsync(input.Username, input.Password) AccountController.cs:53

Controller 只負責轉交與導頁，密碼比對的邏輯一行都不寫在這裡。 _authService 的型別是介面 IAuthService，實作由 01 啟動流程第 4 步的 DI 決定。 

// 步驟 2：交給 AuthService 驗證帳密 + 載入角色
var user = await _authService.ValidateAsync(input.Username, input.Password);
if (user is null)
{
    // 故意不告知是「帳號錯」還是「密碼錯」，避免讓攻擊者列舉帳號
    ModelState.AddModelError(string.Empty, "帳號或密碼錯誤，或帳號已停用");
    return View(input);
}
5 _db.UserAccounts.Include(u => u.UserRoles).ThenInclude(ur => ur.Role) Services/AuthService.cs:30–33

刻意一次把角色一起載入（Eager Loading）。 因為第 9 步馬上就要用角色名稱產生 Claims，分兩次查會多跑一趟資料庫。 

// 步驟 1：查帳號（含 Roles 一起載入，登入後就能直接寫入 Claims）
var user = await _db.UserAccounts
    .Include(u => u.UserRoles)
        .ThenInclude(ur => ur.Role)
    .FirstOrDefaultAsync(u => u.Username == username);
6 → UserAccount? （查無帳號則為 null） Services/AuthService.cs:35

EF Core 把這段 LINQ 翻成一句含 LEFT JOIN 的 SQL。 回傳型別是 可為 null 的 UserAccount?—— 「查不到」在這裡是正常結果，不是例外。 

if (user is null) return null;
7 IsActive 檢查 → _passwordHasher.Verify(password, user.PasswordHash) Services/AuthService.cs:37–43

三道檢查全部回傳同一個 null， 所以外面無從分辨是「查無此人」「已停用」還是「密碼錯」。 BcryptPasswordHasher 內部呼叫 BCrypt.Net.BCrypt.Verify， 雜湊本身含隨機 salt，所以同樣的密碼每次存進去的字串都不一樣。 

// 步驟 2：拒絕停用帳號
if (!user.IsActive) return null;

// 步驟 3：比對密碼雜湊
if (!_passwordHasher.Verify(password, user.PasswordHash)) return null;

return user;
8 _authService.SignInAsync(HttpContext, user, input.RememberMe) AccountController.cs:62

驗證成功才進入「簽入」。注意這裡把 HttpContext 傳進 Service—— 因為寫 Cookie 需要當下這個回應物件。 

// 步驟 3：寫入 Cookie 完成登入
await _authService.SignInAsync(HttpContext, user, input.RememberMe);
9 Claims → ClaimsIdentity → ClaimsPrincipal Services/AuthService.cs:52–70

這一段是整個授權系統的地基。 每個角色被加成一筆 ClaimTypes.Role； 之後所有 [Authorize(Roles = "Tutor,SectionChief,BranchDirector")] 比對的就是這些字串。NameIdentifier 存的是 user.Id， 後面每一條流程用來認「目前登入者是誰」的 GetCurrentUserId() 讀的也是它。 

var claims = new List<Claim>
{
    new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
    new Claim(ClaimTypes.Name, user.DisplayName),
    new Claim("Username", user.Username)
};

// 步驟 2：每個角色加一筆 Claim（[Authorize(Roles="Admin")] 會比對這些）
foreach (var ur in user.UserRoles)
{
    if (ur.Role is not null)
        claims.Add(new Claim(ClaimTypes.Role, ur.Role.Name));
}

var identity = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
var principal = new ClaimsPrincipal(identity);
10 context.SignInAsync(scheme, principal, properties) Services/AuthService.cs:73–83

ASP.NET Core 內建方法把 ClaimsPrincipal 序列化 → 加密 → 簽章，寫成一個 Set-Cookie 回應標頭。 因為有簽章，使用者沒辦法自己改 Cookie 把角色改成 Admin。 

var properties = new AuthenticationProperties
{
    IsPersistent = isPersistent,                    // 勾「記住我」才持久化
    ExpiresUtc = DateTimeOffset.UtcNow.AddHours(8)  // Cookie 有效 8 小時
};

await context.SignInAsync(
    CookieAuthenticationDefaults.AuthenticationScheme, principal, properties);
11 Url.IsLocalUrl(input.ReturnUrl) ? Redirect(…) : RedirectToAction("Index", "Home") AccountController.cs:65–70

Url.IsLocalUrl 是必要的安全檢查： 沒有它，攻擊者可以做出 /Account/Login?returnUrl=https://evil.example 這種連結， 使用者登入成功後就被送到外部網站（Open Redirect）。 

// 步驟 4：導回原本要去的頁面（如果有）
if (!string.IsNullOrEmpty(input.ReturnUrl) && Url.IsLocalUrl(input.ReturnUrl))
{
    return Redirect(input.ReturnUrl);
}

return RedirectToAction("Index", "Home");
12 app.UseAuthentication() 每個請求還原身分 Program.cs:122–123

之後每個請求，UseAuthentication() 都會解開 Cookie 還原成 HttpContext.User，接著 UseAuthorization() 拿它去比對 [Authorize]。登入狀態沒有存在伺服器記憶體裡—— 重啟網站不會把大家踢下線，因為身分完全帶在 Cookie 上。 

app.UseAuthentication();   // Cookie → ClaimsPrincipal（你是誰）
app.UseAuthorization();    // 比對 [Authorize(Roles=…)]（你能不能）

關鍵設計決策

決策為什麼
不用 ASP.NET Core Identity Identity 帶進來一整套使用者/角色/宣告資料表與 UI， 對本專案（自訂 UserAccount + Cohort 關聯）反而是包袱。 自己實作 3 個方法就夠，也比較容易讀懂發生了什麼事。
登入失敗只給一句籠統訊息 若分別回「查無此帳號」與「密碼錯誤」，攻擊者可以用它列舉出有效帳號。
登出用 POST 不用 GET 見 AccountController.cs:77–80。 GET 版的登出網址可以被塞進 <img src>，讓別人一開頁面就被登出。
角色寫進 Cookie 而非每次查 DB 省下每個請求一次查詢。代價是改了角色要重新登入才生效—— /Admin/Users/Edit 改完角色後請記得這件事。

自己動手驗證

  1. 在 AuthService.cs:44（Verify 那行）設中斷點，用 Admin / Admin@123 登入， 觀察 user.PasswordHash 長什麼樣（$2a$… 開頭就是 BCrypt）。
  2. 用同一組密碼替兩個帳號設密碼，比對它們的 PasswordHash——會不一樣， 因為每次都用了新的隨機 salt。
  3. 登入後按 F12 → Application → Cookies，找到 LeaveSystem.Auth， 試著改掉其中幾個字元再重新整理，會被當成未登入踢回登入頁（簽章驗證失敗）。
  4. 用學員帳號登入後直接開 /Admin/Users，看它轉到 /Account/AccessDenied—— 這就是第 5 步 AccessDeniedPath 設定在起作用。
