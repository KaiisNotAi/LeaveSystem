2. 報表與統計

三個查詢頁，共用一個 LeaveReportService：

頁面誰能看內容
/Reports學員依狀態 / 假別 / 日期篩選自己的請假單
/Reports/Summary學員各假別累計時數 + 班期上限進度條

2.1 關鍵設計一：統計口徑要一致

只累計 Status == Approved

這跟第 11 章規則 3的上限檢查必須是同一個口徑。

不然會出現「進度條說我用了 30 小時，但送單時卻說我用了 20 小時」這種 使用者完全無法理解的狀況。

凡是同一個數字在兩個地方出現，就要確認算法一致。 這種 bug 不會報錯，只會讓人不信任你的系統。

2.2 關鍵設計二：什麼時候把資料拉回記憶體

C#取自完成品：Services/LeaveReportService.cs:106
// 篩選在資料庫端做（WHERE 進得了 SQL）
var approved = await _db.LeaveRequests
    .AsNoTracking()
    .Include(r => r.LeaveType)
    .Where(r => r.StudentId == studentId && r.Status == LeaveStatus.Approved)
    .ToListAsync();          // ← 這裡拉回記憶體

// 分組與排序在記憶體端做
var items = approved
    .GroupBy(r => new { r.LeaveTypeId, r.LeaveType.Name, r.LeaveType.SortOrder })
    .OrderBy(g => g.Key.SortOrder)
    .Select(g => new { g.Key.Name, Total = g.Sum(r => r.TotalHours), Count = g.Count() })
    .ToList();
為什麼 GroupBy 要在記憶體做

GroupBy 在不同資料庫 provider 的翻譯行為有差異， 尤其還要同時依關聯表的欄位排序時，容易翻譯失敗或產生怪異的 SQL。

但這是有條件的取捨：單一學員的假單量本來就不大（幾十筆）。 如果資料量是整個機構幾萬筆，就該改成資料庫端的 GROUP BY 或用檢視表。 知道自己在做什麼取捨，比選哪一邊更重要。

自己動手 參考 循序圖教學站 · 06 紀錄查詢與時數統計（9 步）， 以及完成品的 Services/LeaveReportService.cs、Controllers/ReportsController.cs。

3. 曠課紀錄與雙 Controller

曠課跟請假完全不同：請假是事前申請、要簽核； 曠課是事後行政登錄的既成事實，沒有簽核流程。

3.1 稽核欄位不能在 Update 時覆寫

C#取自完成品：Services/AbsenceRecordService.cs
// CreateAsync：稽核欄位只在這裡寫入一次
var record = new AbsenceRecord
{
    StudentId = input.StudentId, OccurredAt = input.OccurredAt, Hours = input.Hours,
    CreatedByUserId = createdByUserId,      // ← 只有這裡
    CreatedAt       = DateTime.UtcNow       // ← 只有這裡
};

// UpdateAsync：刻意「不碰」這兩個欄位
record.StudentId  = input.StudentId;
record.OccurredAt = input.OccurredAt;
record.Hours      = input.Hours;
record.Note       = NormalizeNote(input.Note);
為什麼 如果 Update 也寫 CreatedByUserId = 目前使用者， 那 A 建立、B 只改了一個錯字，紀錄就變成「B 建立的」。 稽核資訊的意義是「最初是誰放進來的」，一旦被覆寫就毫無價值。

3.2 兩個同名 Controller

專案裡有兩個都叫 AbsenceRecordsController 的類別： Controllers/AbsenceRecordsController.cs（學員自查，唯讀）與 Controllers/Admin/AbsenceRecordsController.cs（行政管理，CRUD）。

陷阱：Razor 會找錯 View

第 3 章第 3 條約定： return View() 去找 Views/{Controller 名}/。 兩個都叫 AbsenceRecords， 所以行政端會載入到學員端的 View，然後因為 ViewModel 型別不合而爆掉。

C#解法：取自完成品 Program.cs:27
// 在 View 搜尋清單「最前面」插一條路徑
builder.Services.Configure<RazorViewEngineOptions>(options =>
{
    options.ViewLocationFormats.Insert(0, "/Views/Admin/{1}/{0}.cshtml");
});

這樣 Admin 版就會優先命中 Views/Admin/AbsenceRecords/。 再配上 [Route("Admin/AbsenceRecords/{action=Index}/{id?}")] 分開網址，兩者就能共存。

自己動手 這個功能有一份專門的詳細文件： docs/10-曠課紀錄教學.md， 涵蓋兩層下拉選單的選型理由、日期「含當天」的處理、七個常見問題。 搭配 循序圖教學站 · 07 曠課紀錄 看。

4. 通知與 Email

送單、轉關、核准、駁回、取消時，要通知對的人。 完成品用一個 NotificationDispatcher 統一處理， 雙軌派送：站內通知 + Email。

4.1 本章最重要的一課：通知失敗不能拖垮主流程

C#取自完成品：Services/Notifications/NotificationDispatcher.cs:135
private async Task DispatchAsync(UserAccount recipient, string title, string message, string url, …)
{
    try
    {
        await _notifications.CreateAsync(recipient.Id, title, message, url);
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "站內通知寫入失敗（UserId={UserId}）", recipient.Id);
        // 不往上拋！繼續往下走去寄 Email
    }

    if (!string.IsNullOrWhiteSpace(recipient.Email))
    {
        try
        {
            await _emails.SendAsync(recipient.Email!, title, message, …);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Email 派送失敗（UserId={UserId}）", recipient.Id);
        }
    }
}
為什麼要把例外吞掉（這通常是壞習慣）

因為通知是在 SaveChangesAsync() 之後才呼叫的—— 簽核已經是既成事實了。

這時候如果 SMTP 伺服器剛好掛了、通知丟出例外， 使用者會看到一個 500 錯誤頁， 誤以為簽核失敗而重簽一次——但第二次會被 第 ③ 道防線擋下來， 他就會以為系統壞了。

原則：「附帶效果」失敗，不能讓「主要動作」看起來失敗。 但一定要寫 log，不然問題會被靜靜吃掉。

4.2 開發時怎麼測 Email

不用真的架 SMTP 伺服器。MailKit 支援把信寫成檔案：

JSONappsettings.Development.json
"Email": {
  "Mode": "PickupDirectory",
  "PickupDirectory": "./mail-pickup",
  "From": "noreply@leavesystem.local"
}

每封信會變成 ./mail-pickup/xxx.eml，用記事本就能打開檢查內容。 上線時把 Mode 改成 Smtp 即可，程式碼一行都不用動。

自己動手 參考 循序圖教學站 · 05 站內通知 + Email（11 步）， 裡面也解釋了 NullNotificationDispatcher 這個「什麼都不做的實作」在測試裡的用途。 設定細節在 docs/11-Email通知設定.md。

5. 匯出 CSV / Excel

一次 GET 產生一個含三個工作表的 .xlsx。關鍵設計是欄位定義只寫一份：

C#取自完成品：Controllers/Admin/ExportController.cs:197
private static readonly IReadOnlyList<ExportColumn<AdminLeaveDetailRow>> LeaveDetailColumns = new[]
{
    new ExportColumn<AdminLeaveDetailRow>("班期", r => r.CohortName),
    new ExportColumn<AdminLeaveDetailRow>("起始", r => r.StartAt,    ExportValueType.DateTime),
    new ExportColumn<AdminLeaveDetailRow>("時數", r => r.TotalHours, ExportValueType.Hours),
    // …
};

同一份定義同時餵給 CSV 與 Excel 兩個輸出器， 所以兩種格式的欄位順序與標題永遠一致，要加一欄只要改一個地方。

5.1 兩個一定要知道的細節

細節為什麼
CSV 要加 UTF-8 BOM Excel 開純 UTF-8（無 BOM）的 CSV 時，中文會變亂碼—— 它會猜成系統的 ANSI 編碼。加那 3 個位元組就正常了。
日期與數字不要輸出成字串 Excel 儲存格如果是文字，使用者就沒辦法排序、沒辦法加總、沒辦法做樞紐分析。 要用原生型別。
自己動手 參考 循序圖教學站 · 08 匯出 CSV / Excel（10 步）， 裡面解釋了 ExportSheet.Create<T> 怎麼用「型別擦除」讓三種不同型別的資料 塞進同一個 ExportWorkbook 呼叫。

6. 接下來學什麼

照優先順序排，前三個是實務上最快用得到的：

主題為什麼值得學
分頁與搜尋 你的清單頁現在是「全部撈出來」。 資料一多就會慢到不能用。Skip() / Take() 是最基本的功課。
記錄與診斷
（ILogger）		 上線之後你沒辦法設中斷點。 log 是唯一能知道發生什麼事的方式。
部署 IIS 或 Docker、環境變數管理連線字串、 正式環境的 Migration 該怎麼跑。
Web API + 前端框架 MVC 是「伺服器產生 HTML」。 現在很多專案改成「後端出 JSON、前端用 React/Vue 畫」。 dotnet new webapi 開始。
ASP.NET Core Identity 本書自己做了登入。Identity 是官方的完整方案： 註冊、忘記密碼、Email 驗證、雙因素、外部登入。 先自己做過一遍再用它，你會知道它在幫你做什麼。
整合測試
（WebApplicationFactory）		 你現在測的是 Service。 整合測試可以連 HTTP 請求一起測，含路由與授權。

8. 最後幾句

你學到最重要的東西，其實不是語法

asp-for 怎麼寫、Include 放哪裡，這些查得到。

真正重要的是那些「為什麼」： 為什麼業務規則要離開 Controller（才測得動）、 為什麼身分只能從 Cookie 取（不然誰都能看別人的資料）、 為什麼簽核人不在送單時寫死（換人才不會卡住）、 為什麼通知失敗不能拖垮簽核（不然使用者會重簽）。

這些判斷換到別的語言、別的框架一樣成立。 語法會過時，這些不會。
