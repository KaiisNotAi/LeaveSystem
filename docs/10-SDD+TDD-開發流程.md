# 10 — SDD + TDD 開發流程

本文件定義本專案後續建議採用的「規格驅動 + 測試驅動」流程，目標是：
- 先把需求說清楚（SDD）
- 再用測試保護規則（TDD）
- 最後才寫最小可行實作

---

## 1. 什麼是 SDD + TDD

- **SDD（Spec-Driven Development）**：先定義規格，再動手寫程式。
- **TDD（Test-Driven Development）**：先寫失敗測試（Red），再寫程式讓測試通過（Green），最後重構（Refactor）。

本專案採用方式：
1. 先把規格寫在 `docs/*.md`（可讀、可對齊）
2. 再把規格轉成 `LeaveSystem.Tests` 測試案例（可執行）
3. 最後改正式程式（可驗證）

---

## 2. 每個功能的固定步驟

1. **規格切片（SDD）**
   - 把需求拆成可驗收句子（Given / When / Then）。
   - 每條規格至少對應一個測試案例。

2. **先寫測試（TDD - Red）**
   - 新增測試方法，先讓它失敗。
   - 測試名稱要描述業務語意（例：`TryCalculate_11To14_ShouldSkipLunchAndReturn2Hours`）。

3. **最小實作（TDD - Green）**
   - 只寫讓當前測試通過的最少程式。
   - 避免一次加太多邏輯，確保每次改動可追蹤。

4. **重構（TDD - Refactor）**
   - 整理命名、抽方法、提升可讀性。
   - 重構後測試仍需全綠。

5. **手動驗收（UI 流程）**
   - 用真實角色登入操作，確認頁面與訊息符合規格。

---

## 3. 測試分層建議

### 3.1 單元測試（優先）
- 目標：純邏輯服務（如 `LeaveCalculator`）。
- 特性：快速、穩定、回饋即時。

### 3.2 整合測試（次階）
- 目標：Controller + DbContext + 交易流程。
- 驗證主檔/子檔是否正確落庫。

### 3.3 手動測試（保留）
- 目標：角色操作與 UI 呈現。
- 用於確認「使用者真的能完成任務」。

---

## 4. Definition of Done（完成定義）

每個功能完成需同時達成：
1. 規格文件已更新（SDD）
2. 核心規則有測試覆蓋（TDD）
3. `dotnet build` 成功
4. `dotnet test` 全綠
5. 關鍵 UI 手動驗證通過
