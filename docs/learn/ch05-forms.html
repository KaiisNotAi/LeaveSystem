1. 一個表單需要兩個 Action

「新增一筆資料」這件事，在瀏覽器上其實是兩次獨立的請求：

第幾次HTTP 方法做什麼
第一次GET使用者點「新增」→ 伺服器回一張空白表單
第二次POST使用者填完按送出 → 伺服器收下資料並處理

所以 Controller 裡會有兩個同名方法，用屬性區分：

C#表單的標準骨架
[HttpGet]
public IActionResult Create()
{
    return View();                // 給空白表單
}

[HttpPost]
public IActionResult Create(LeaveTypeCreateViewModel input)
{
    // 收資料、驗證、存檔
}
同名方法不會打架嗎？

C# 允許同名但參數不同的方法（叫「多載」）。 [HttpGet] 那個沒參數、[HttpPost] 那個有一個參數，所以編譯得過。

路由則是靠 [HttpGet] / [HttpPost] 屬性來決定 「這次請求該給哪一個」。GET 的那個可以省略屬性（預設就是 GET）， 但寫出來比較清楚。

2. ViewModel：為什麼不直接用 Entity

你已經有 Models/LeaveType.cs 了，直接拿它當表單的模型不行嗎？ 能動，但會出兩種問題。

問題一：使用者可以塞你沒打算讓他填的欄位

表單上只放了「名稱」和「代碼」，但 LeaveType 還有 Id。 使用者可以自己在瀏覽器開發者工具加一個 <input name="Id" value="999">， 模型繫結會照單全收。

這叫「Over-posting」。在有 IsAdmin、PasswordHash 這種欄位的類別上，後果就很嚴重了。

問題二：畫面需要的東西，資料表不會有

例如「確認密碼」欄位、下拉選單的選項清單、 「我同意條款」的勾選框——這些都不該存進資料表， 但表單需要它們。

解法是另外做一個只為這個畫面而生的類別，叫 ViewModel：

新增檔案Models/ViewModels/LeaveTypeCreateViewModel.cs
using System.ComponentModel.DataAnnotations;

namespace MyLeaveSystem.Models.ViewModels;

public class LeaveTypeCreateViewModel
{
    [Required(ErrorMessage = "請填寫假別名稱")]
    [StringLength(20, ErrorMessage = "假別名稱不可超過 20 個字")]
    [Display(Name = "假別名稱")]
    public string Name { get; set; } = string.Empty;

    [Required(ErrorMessage = "請填寫代碼")]
    [RegularExpression("^[A-Z_]+$", ErrorMessage = "代碼只能用大寫英文與底線")]
    [Display(Name = "代碼")]
    public string Code { get; set; } = string.Empty;

    [Range(1, 99, ErrorMessage = "排序必須介於 1 到 99")]
    [Display(Name = "排序")]
    public int SortOrder { get; set; } = 1;

    [StringLength(100)]
    [Display(Name = "說明")]
    public string? Description { get; set; }
}

沒有 Id、沒有 IsActive—— 使用者塞什麼都沒用，因為這個類別根本沒有那些屬性。

屬性作用
[Required]必填
[StringLength(20)]最長 20 個字
[Range(1, 99)]數值範圍
[RegularExpression(…)]要符合這個規則運算式
[Display(Name = "假別名稱")] 顯示用的中文標籤。錯誤訊息裡也會用它， 所以有寫的話訊息會是「假別名稱 是必要欄位」而不是「Name 是必要欄位」。

3. 動手：新增假別表單

3.1 讓資料活過一次請求

資料庫要到第 6 章才會有。這一章先用一個 static 清單暫存，讓你能專心在表單本身。

asp-for 一個屬性做了四件事

寫 <input asp-for="Name" />，Razor 產生出來的是：

<input id="Name" name="Name" value="" type="text" data-val="true" data-val-required="請填寫假別名稱" ... />

① name（POST 回來時靠它對應）、 ② id（給 <label> 用）、 ③ value（重填時保留使用者輸入）、 ④ data-val-*（前端驗證規則，從你的 [Required] 讀來的）。

<label asp-for="Name"> 則會自動用 [Display(Name = "假別名稱")] 當文字——所以標籤裡是空的。

3.3 POST：收下並驗證

修改Controllers/LeaveTypesController.cs
[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Create(LeaveTypeCreateViewModel input)
{
    // ① 欄位層級的驗證（來自 [Required] 那些屬性）
    if (!ModelState.IsValid)
    {
        return View(input);       // 把使用者填過的內容一起送回去
    }

    // ② 業務規則的驗證（屬性做不到的）
    if (_types.Any(t => t.Code == input.Code))
    {
        ModelState.AddModelError(nameof(input.Code), "這個代碼已經被用了");
        return View(input);
    }

    // ③ 通過了，才建立實體
    _types.Add(new LeaveType
    {
        Id          = _types.Count == 0 ? 1 : _types.Max(t => t.Id) + 1,
        Name        = input.Name.Trim(),
        Code        = input.Code.Trim().ToUpperInvariant(),
        SortOrder   = input.SortOrder,
        Description = string.IsNullOrWhiteSpace(input.Description) ? null : input.Description.Trim(),
        IsActive    = true
    });

    TempData["Success"] = $"已新增假別「{input.Name}」";
    return RedirectToAction(nameof(Index));    // ④ 一定要轉址
}

4. 模型繫結是怎麼運作的

使用者按下送出時，瀏覽器實際傳給伺服器的是一堆純文字的鍵值對：

HTTPPOST 請求主體
Name=產假&Code=MATERNITY&SortOrder=5&Description=&__RequestVerificationToken=CfDJ8...

模型繫結做的事，就是把它變回一個 C# 物件：

  1. 看 Action 參數的型別是 LeaveTypeCreateViewModel
  2. 逐一列出它的屬性：Name、Code、SortOrder、Description
  3. 從請求裡找同名的值（先找表單、再找路由、再找查詢字串）
  4. 轉型："5" → int 5。轉不過去就記一筆錯誤到 ModelState（例如排序填「abc」）
  5. 跑資料註解驗證（[Required] 那些），不合格的也記進 ModelState
所以 ModelState 裡有兩種錯誤 轉型失敗（「abc」不是數字）與驗證失敗（沒填、太長）。 兩種都在 !ModelState.IsValid 這一關被擋下來， 而且都會被 asp-validation-for 顯示在對應欄位旁邊。

5. 驗證與 ModelState

驗證有三層，缺一不可：

層在哪裡擋什麼 / 為什麼需要
前端 瀏覽器 JavaScript
（_ValidationScriptsPartial）		 使用者體驗：不用送出就知道填錯了。
完全不能信任——關掉 JS 就沒了。
後端欄位 [Required] 等屬性
→ ModelState.IsValid		 真正的防線。格式、長度、範圍、必填。
後端業務 Controller / Service 裡自己寫 屬性做不到的：「代碼不能重複」要查資料才知道、 「請假不能超過班期上限」要算才知道。
絕對不要只做前端驗證

任何人都可以用工具直接對你的 /LeaveTypes/Create 送 POST， 完全跳過你的網頁與 JavaScript。

前端驗證是「體貼」，後端驗證是「安全」。 前端可以省，後端不能省。

5.1 兩種加錯誤的方式

C#AddModelError 的兩種用法
// 綁在某個欄位上 → 顯示在該欄位的 asp-validation-for 位置
ModelState.AddModelError(nameof(input.Code), "這個代碼已經被用了");

// 不綁欄位 → 顯示在 asp-validation-summary="ModelOnly" 的區塊
ModelState.AddModelError(string.Empty, "系統設定不完整，請聯絡管理員");
用 nameof 不要用字串 寫 nameof(input.Code) 而不是 "Code"： 將來屬性改名時，編譯器會強迫你一起改， 寫死字串則會悄悄失效，錯誤訊息就再也不顯示了。

6. 防偽權杖：擋掉 CSRF

先看攻擊長什麼樣。假設你的網站有一個「刪除假別」的 POST：

HTML攻擊者放在自己網站上的東西
<form action="https://你的網站/LeaveTypes/Delete/1" method="post" id="evil"></form>
<script>document.getElementById('evil').submit();</script>

管理員登入你的網站後，在同一個瀏覽器打開了攻擊者的頁面。 瀏覽器會自動帶上你網站的 Cookie，於是這個 POST 看起來就像是管理員自己按的。

防禦方式是防偽權杖：

  1. Razor 的 <form method="post"> 會自動塞一個隱藏欄位 __RequestVerificationToken，值是隨機的
  2. 同時發一個對應的 Cookie
  3. [ValidateAntiForgeryToken] 檢查兩者是否配對

攻擊者拿不到那個隨機值（瀏覽器的同源政策讓他讀不到你網站的頁面內容）， 所以偽造的表單一定會被擋下來。

規則很簡單 每一個 [HttpPost] 都要配一個 [ValidateAntiForgeryToken]。 你去看完成品專案，LeaveRequestsController、ApprovalsController、 AccountController 的每一個 POST 都有。 GET 不需要——因為 GET 本來就不該改變任何資料。
自己手寫 <form> 會漏掉權杖

用 <form asp-action="Create">（Tag Helper）才會自動加。 如果你寫 <form action="/LeaveTypes/Create">（純 HTML）， 就不會有權杖，送出時會得到 400 Bad Request。

真的需要手寫的話，在表單裡加 @Html.AntiForgeryToken()。

7. PRG：為什麼一定要轉址

Post → Redirect → Get。 存檔成功後不要 return View()，要 return RedirectToAction(...)。

不這樣做的話：

  1. 使用者送出表單（POST），你直接回一個畫面
  2. 網址列還停在 /LeaveTypes/Create，而且瀏覽器記得「這頁是 POST 來的」
  3. 使用者按 F5 重新整理
  4. 瀏覽器問「要重新送出表單嗎？」，使用者按確定
  5. 又新增了一筆一模一樣的資料

改成轉址之後，第 2 步結束時瀏覽器已經跳到 /LeaveTypes（GET）， 按 F5 重送的是那個 GET，什麼事都不會發生。

這也是 TempData 存在的理由 因為中間隔了一次轉址，ViewData 早就沒了。 TempData 是專門設計來撐過這一次轉址的， 而且讀取後就自動消失——所以成功訊息不會在你下次進清單頁時又冒出來。

8. 這個模式你會用一輩子

把這一章的骨架記起來，後面每個新增/編輯頁都是它的變形：

C#MVC 表單處理的標準骨架
[HttpGet]
public IActionResult Create()
    => View(new XxxViewModel());

[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Create(XxxViewModel input)
{
    if (!ModelState.IsValid)          // ① 欄位驗證
        return View(input);

    if (/* 業務規則不符 */)            // ② 業務驗證
    {
        ModelState.AddModelError(/* … */);
        return View(input);
    }

    // ③ 真的做事

    TempData["Success"] = "…";       // ④ PRG
    return RedirectToAction(nameof(Index));
}
