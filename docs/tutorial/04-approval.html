簽核引擎：核准與駁回

03 送單把 N 關空白的 LeaveRequestStep 建好了， 這條流程負責一關一關把它填完。核心只有兩個問題： 「這個人有沒有資格簽這一關？」（EnsureCanActAsync 五道防線）與 「簽完之後是轉下一關還是整張結案？」（ApprovalOutcome）。

private static int? GetAssignedApproverId(LeaveRequestStep step)
{
    var cohort = step.LeaveRequest.Student.Cohort;
    if (cohort is null) return null;

    return step.ApproverRole switch
    {
        RoleTutor          => cohort.TutorUserId,
        RoleSectionChief   => cohort.SectionChiefUserId,
        RoleBranchDirector => cohort.BranchDirectorUserId,
        _ => null
    };
}

駁回 Reject：差在哪裡

RejectAsync（ApprovalService.cs:108）跟核准共用第 3~6 步的載入與五道防線， 只有三個地方不同：

差異核准 ApproveAsync駁回 RejectAsync
意見是否必填 可留白 必填（:110–113 最先檢查，空白直接退回）
對整張單的效果 轉下一關 或 結案為 Approved 直接 Status = Rejected，不管還剩幾關
通知對象 下一關簽核人 或 學員 一律通知學員，並附上駁回原因
為什麼駁回不用「退回上一關」
三級簽核的實務是「任一關不同意即結束」，學員修正後重新送一張新單， 比在同一張單上來回改狀態單純，也留得下完整的歷史紀錄。

待辦清單是怎麼算出來的

/Approvals 的「待我簽核」不是簡單的 WHERE ApproverUserId = 我—— 因為 Step 在被簽之前 ApproverUserId 是 null。 GetPendingCoreAsync（ApprovalService.cs:251–309）分兩段做： 

// ① 在資料庫端篩出「角色對得上、且正好停在這一關」的候選
var candidates = await _db.LeaveRequestSteps
    .Include(…)
    .Where(s =>
        s.Decision == ApprovalDecision.Pending &&
        s.LeaveRequest.Status == LeaveStatus.Pending &&
        s.Level == s.LeaveRequest.CurrentLevel &&      // ← 只有「當前這一關」才算待辦
        roleNames.Contains(s.ApproverRole))
    .AsNoTracking().ToListAsync();

// ② 在記憶體端用班期指派過濾（switch 運算式翻不成 SQL）
var filtered = candidates.Where(s => GetAssignedApproverId(s) == currentUserId).ToList();

// ③ 一次批次查所有相關學員的已核准時數，避免 N+1
var approvedByStudent = await _db.LeaveRequests
    .Where(r => studentIds.Contains(r.StudentId) && r.Status == LeaveStatus.Approved)
    .GroupBy(r => r.StudentId)
    .Select(g => new { StudentId = g.Key, Sum = g.Sum(r => r.TotalHours) })
    .ToDictionaryAsync(x => x.StudentId, x => x.Sum);
第 ③ 段為什麼要特別寫成批次查詢
待辦清單每一列都要顯示「這位學員已請 X / 上限 Y」。 若在迴圈裡逐一 SumAsync，20 筆待辦就是 20 次資料庫往返（N+1 問題）。 先收集 studentIds 一次查完再查字典，永遠只有 1 次。

自己動手驗證

  1. 用非該班期的導師帳號登入，把 URL 直接改成別班的 /Approvals/Details/{id}，看第 5 道防線把它擋下來。
  2. 在 ApprovalService.cs:82（if (nextStep is not null)）設中斷點， 分別簽一張1 關與一張3 關的單， 觀察 outcome 走進不同分支。
  3. 開兩個瀏覽器分頁，同一張單的簽核頁按兩次核准—— 第二次會被第 3 道防線擋成「本關已簽核」。
  4. 駁回時把意見留空送出，看 RejectAsync 在連資料都還沒查之前就回錯誤。
  5. 在 /Admin/Cohorts/Edit 把班期導師換成另一個人， 重新整理原導師的 /Approvals——待辦立刻消失，出現在新導師那邊。
