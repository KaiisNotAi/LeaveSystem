Flow 05 · Notification & Email Dispatch

站內通知 + Email 雙軌派送

送單與簽核流程都只呼叫一行 NotifyXxxAsync(leaveRequestId)， 剩下的全部由 NotificationDispatcher 負責： 查出這一關該通知誰、組出標題與內文、同時寫進站內通知與寄出 Email。 整個檔案最重要的設計是「通知失敗絕不能讓簽核跟著失敗」。

5 ResolveApproverUserId(req.Student.Cohort, currentStep.ApproverRole) Services/Notifications/NotificationDispatcher.cs:167–173

跟 04 簽核第 6 步的 GetAssignedApproverId 是同一條規則的兩份實作：角色字串 → 班期上對應的 UserId。 兩邊必須一致，否則會出現「通知了 A，但只有 B 簽得下去」的錯亂。 

private static int? ResolveApproverUserId(Cohort cohort, string role) => role switch
{
    RoleTutor          => cohort.TutorUserId,
    RoleSectionChief   => cohort.SectionChiefUserId,
    RoleBranchDirector => cohort.BranchDirectorUserId,
    _ => null
};
這是一個已知的重複

11 最外層 try/catch 保證不往上拋 Services/Notifications/NotificationDispatcher.cs:106, 129–132

NullNotificationDispatcher：測試用的空實作

檔案最後（NotificationDispatcher.cs:182–189）還有一個什麼都不做的實作： 

public class NullNotificationDispatcher : INotificationDispatcher
{
    public Task NotifySubmittedAsync(int id, CancellationToken ct = default) => Task.CompletedTask;
    public Task NotifyApprovedNextAsync(int id, CancellationToken ct = default) => Task.CompletedTask;
    // …其餘同理
}

這是 Null Object 模式。測試 ApprovalService 的簽核邏輯時，不想每次都連帶測到通知與 Email， 就把這個空實作注進去——比在 Service 裡到處寫 if (_notifications != null) 乾淨得多。 正式環境注入哪一個，由 01 啟動流程第 4 步的 DI 決定。

自己動手驗證

  1. 送出一張請假單，然後打開專案根目錄的 mail-pickup/ 資料夾—— 裡面會多一個 .eml 檔，用記事本開就能看到剛才組出來的標題與內文。
  2. 把某個簽核人帳號的 Email 欄位清空，再送一張單： 站內通知照樣進來，但不會產生 .eml。
  3. 在 NotificationService.CreateAsync 第一行故意 throw new Exception("test")，然後簽核一張單—— 簽核仍然成功，只是通知沒進來、Output 視窗多一行 LogError。 看過就改回來。
  4. 把 appsettings.json 的 Email:Mode 改成 "Smtp" 但不啟動任何 SMTP 伺服器，再簽核一次：Email 那軌會失敗並寫 log， 但站內通知與簽核都不受影響。
  5. 在 NotificationDispatcher.cs:116（ResolveApproverUserId）設中斷點， 簽核一張 3 關的單，看第 2 關通知的收件人是科長而不是導師。
