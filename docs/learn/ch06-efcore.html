1. ORM 是什麼、為什麼要用

資料庫講的是 SQL、表格、資料列。C# 講的是類別、物件、集合。 ORM（物件關聯對應）就是中間的翻譯官。

資料庫的世界C# 的世界
資料表 LeaveTypes類別 LeaveType
欄位 Name nvarchar(20)屬性 public string Name { get; set; }
一列資料一個物件實體
SELECT * FROM LeaveTypes WHERE IsActive = 1 db.LeaveTypes.Where(t => t.IsActive)
為什麼不自己寫 SQL 就好？

① 型別安全。SQL 字串打錯要執行才知道； LINQ 打錯編譯就失敗。改了屬性名稱，編譯器會幫你找出所有要改的地方。

② SQL Injection。自己拼字串 SQL 很容易寫出 "… WHERE Name = '" + name + "'"， 使用者輸入 ' OR '1'='1 就能撈走全部資料。 EF Core 一律用參數化查詢，從根本上不會有這個問題。

③ Migration。改了類別，一行指令就能把資料表跟著改， 而且改動有版本紀錄可以進 git。這是第 6 節的主題。

3. Entity：一個類別 = 一張表

好消息：你的 Models/LeaveType.cs 已經可以直接當 Entity 用了。 只要按照幾個慣例，EF Core 就看得懂。

把它移到 Models/Entities/ 資料夾（跟完成品專案一致），並補上資料庫用的屬性：

修改Models/Entities/LeaveType.cs（從 Models/ 移過來）
using System.ComponentModel.DataAnnotations;

namespace MyLeaveSystem.Models.Entities;

public class LeaveType
{
    // 慣例：叫 Id 或 LeaveTypeId 的屬性，會自動變成主鍵 + 自動編號
    public int Id { get; set; }

    [Required]
    [MaxLength(20)]        // → nvarchar(20)，不寫的話是 nvarchar(max)
    public string Name { get; set; } = string.Empty;

    [Required]
    [MaxLength(30)]
    public string Code { get; set; } = string.Empty;

    public bool IsActive  { get; set; } = true;
    public int  SortOrder { get; set; }

    [MaxLength(100)]
    // string? → 資料庫欄位允許 NULL；string → NOT NULL
    public string? Description { get; set; }
}

記得把用到它的地方 using 改成新的命名空間（Controller 與 _ViewImports.cshtml）。

你寫的資料庫會變成
public int Id主鍵，IDENTITY 自動編號
public string Namenvarchar(…) NOT NULL
public string? Descriptionnvarchar(…) NULL
[MaxLength(20)]nvarchar(20)
public decimal Hoursdecimal(18,2)
public bool IsActivebit

4. AppDbContext

DbContext 代表「一次跟資料庫打交道的工作階段」。 它負責：知道有哪些資料表、追蹤你改了哪些物件、把變更寫回去。

新增檔案Data/AppDbContext.cs
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Models.Entities;

namespace MyLeaveSystem.Data;

public class AppDbContext : DbContext
{
    // 設定（連線字串等）由外面注入進來，這個類別自己不決定連哪個資料庫
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options)
    {
    }

    // 每一個 DbSet<T> = 一張資料表。
    // 屬性名稱（LeaveTypes）就是資料表名稱，習慣用複數。
    public DbSet<LeaveType> LeaveTypes => Set<LeaveType>();
}
為什麼寫 => Set<LeaveType>() 而不是 { get; set; }？ 兩種寫法都能動。=> Set<T>() 是比較新的寫法， 好處是這個屬性永遠不可能是 null， 打開 Nullable 檢查時編譯器不會念你。完成品專案用的也是這種。

5. 連線字串與註冊

5.1 把連線字串寫進設定檔

修改appsettings.json
{
  "Logging": {
    "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" }
  },
  "AllowedHosts": "*",
  "ConnectionStrings": {
    "DefaultConnection": "Server=.;Database=MyLeaveSystem;Trusted_Connection=True;TrustServerCertificate=True;MultipleActiveResultSets=true"
  }
}
片段意思
Server=.本機預設執行個體。
LocalDB 要寫 Server=(localdb)\MSSQLLocalDB；
Docker 要寫 Server=localhost,1433
Database=MyLeaveSystem資料庫名稱。不存在也沒關係，Migration 會幫你建
Trusted_Connection=True用 Windows 帳號登入，不用帳密。
Docker / Linux 要改成 User Id=sa;Password=你的密碼;
TrustServerCertificate=True本機開發用，跳過憑證驗證
正式環境不要把密碼寫在 appsettings.json 本機開發沒關係（而且用 Windows 驗證根本沒密碼）。 但如果連線字串裡有密碼，那個檔案就不該進 git。 正式做法是用環境變數或 User Secrets。

5.2 註冊到 DI 容器

修改Program.cs
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Data;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

builder.Services.AddDbContext<AppDbContext>(options =>
{
    var connectionString = builder.Configuration.GetConnectionString("DefaultConnection")
        ?? throw new InvalidOperationException("找不到連線字串 DefaultConnection");
    options.UseSqlServer(connectionString);
});

var app = builder.Build();

這就是第 2 章說的「上半段：登記服務」。 登記之後，任何 Controller 只要在建構式要求 AppDbContext， 框架就會自動給它一個。下一節就會用到。

6. Migration：讓程式建表

Migration 是「資料庫結構的版本紀錄」。 每次你改了 Entity，就產生一個 Migration，它記錄「這次要怎麼把資料庫從舊結構改成新結構」。

終端機在 MyLeaveSystem 資料夾
dotnet ef migrations add InitialCreate

成功的話會多出一個 Migrations 資料夾。打開裡面那個 …_InitialCreate.cs：

C#Migrations/20260819…_InitialCreate.cs（自動產生，不要手改）
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.CreateTable(
        name: "LeaveTypes",
        columns: table => new
        {
            Id          = table.Column<int>(nullable: false)
                               .Annotation("SqlServer:Identity", "1, 1"),
            Name        = table.Column<string>(maxLength: 20, nullable: false),
            Code        = table.Column<string>(maxLength: 30, nullable: false),
            IsActive    = table.Column<bool>(nullable: false),
            SortOrder   = table.Column<int>(nullable: false),
            Description = table.Column<string>(maxLength: 100, nullable: true)
        },
        constraints: table => table.PrimaryKey("PK_LeaveTypes", x => x.Id));
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropTable(name: "LeaveTypes");   // 反悔時退回去用的
}

注意：到這裡資料庫還是空的。Migration 只是「計畫書」， 要執行它才會真的動到資料庫：

終端機套用到資料庫
dotnet ef database update

現在用 SSMS 連上去看，會有一個 MyLeaveSystem 資料庫， 裡面有 LeaveTypes 表，還有一張 __EFMigrationsHistory—— 那是 EF Core 用來記「哪些 Migration 已經跑過了」的。

Migration 檔案要進版控嗎？要！

Migrations/ 資料夾一定要 commit 進 git。

這樣隊友 pull 下來之後，只要跑一次 dotnet ef database update， 他的資料庫就跟你一模一樣。資料庫結構因此有了版本控制—— 這是 ORM 最被低估的好處。

三個最常見的 Migration 問題

「Unable to create an object of type 'AppDbContext'」
通常是 Program.cs 沒註冊 AddDbContext， 或連線字串讀不到。先確認 dotnet build 過得了。

「A network-related or instance-specific error…」
連不到 SQL Server。檢查服務有沒有啟動、Server= 寫對沒。

產生的 Migration 是空的
代表 EF Core 覺得「跟上次比沒有變化」。 檢查新 Entity 有沒有加到 AppDbContext 的 DbSet。

6.1 之後改 Entity 的固定流程

終端機記起來，後面每一章都會用
# 1. 改 Entity 類別（加欄位、改型別…）
# 2. 產生 Migration（名字取有意義的）
dotnet ef migrations add AddLeaveTypeColorColumn

# 3. 套用到資料庫
dotnet ef database update

# 產生錯了還沒 update 的話，可以移除最後一個
dotnet ef migrations remove

7. 動手：把 static 清單換掉

現在把第 5 章那個暫時的 static 清單換成真的資料庫。

修改Controllers/LeaveTypesController.cs（整個換掉）
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Data;
using MyLeaveSystem.Models.Entities;
using MyLeaveSystem.Models.ViewModels;

namespace MyLeaveSystem.Controllers;

public class LeaveTypesController : Controller
{
    private readonly AppDbContext _db;

    // 建構式注入：你只要「要求」，框架就會給你一個 AppDbContext
    // （因為第 5.2 節在 Program.cs 登記過了）
    public LeaveTypesController(AppDbContext db)
    {
        _db = db;
    }

    public async Task<IActionResult> Index()
    {
        var types = await _db.LeaveTypes
            .OrderBy(t => t.SortOrder)
            .ToListAsync();

        return View(types);
    }

    [HttpGet]
    public IActionResult Create() => View(new LeaveTypeCreateViewModel());

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Create(LeaveTypeCreateViewModel input)
    {
        if (!ModelState.IsValid)
        {
            return View(input);
        }

        var code = input.Code.Trim().ToUpperInvariant();

        // 業務驗證：代碼不能重複（這次是真的去問資料庫）
        if (await _db.LeaveTypes.AnyAsync(t => t.Code == code))
        {
            ModelState.AddModelError(nameof(input.Code), "這個代碼已經被用了");
            return View(input);
        }

        _db.LeaveTypes.Add(new LeaveType
        {
            Name        = input.Name.Trim(),
            Code        = code,
            SortOrder   = input.SortOrder,
            Description = string.IsNullOrWhiteSpace(input.Description) ? null : input.Description.Trim(),
            IsActive    = true
        });

        await _db.SaveChangesAsync();     // ← 這一行才真的寫進資料庫

        TempData["Success"] = $"已新增假別「{input.Name}」";
        return RedirectToAction(nameof(Index));
    }
}

三個變化值得注意：

變化為什麼
方法變成 async Task<IActionResult> 查資料庫要等，用 await 才不會卡住執行緒 （第 1 章第 8 節）
不再有 Id = _types.Max(…) + 1 Id 交給資料庫產生。SaveChangesAsync() 之後， EF Core 會自動把產生的 Id 填回你的物件
多了 SaveChangesAsync() Add() 只是在記憶體裡標記「等一下要新增這個」。 沒有 SaveChangesAsync() 就什麼都不會發生
最常見的 EF Core 新手錯誤：忘記 SaveChanges 改完資料、頁面也正常轉址了，但資料就是沒變—— 九成是漏了 SaveChangesAsync()。 因為不會有任何錯誤訊息，這個 bug 特別難找。

現在跑起來，/LeaveTypes 應該是空的（資料庫是新的）。 用「新增假別」加幾筆，然後重新啟動程式——資料還在。這就是這一章的重點。

8. 種子資料

每次重建資料庫都要手動加四種假別很煩。寫一個「種子」，讓程式啟動時自動補上：

新增檔案Data/SeedData.cs
using MyLeaveSystem.Models.Entities;

namespace MyLeaveSystem.Data;

public static class SeedData
{
    public static void Initialize(AppDbContext db)
    {
        // 關鍵：已經有資料就跳過。這讓它可以重複執行而不會愈長愈多。
        if (db.LeaveTypes.Any()) return;

        db.LeaveTypes.AddRange(
            new LeaveType { Name = "病假", Code = "SICK",        SortOrder = 1, Description = "因病無法到課" },
            new LeaveType { Name = "事假", Code = "PERSONAL",    SortOrder = 2, Description = "個人事務" },
            new LeaveType { Name = "喪假", Code = "BEREAVEMENT", SortOrder = 3, Description = "親屬喪事" },
            new LeaveType { Name = "公假", Code = "OFFICIAL",    SortOrder = 4, Description = "因公務外出" });

        db.SaveChanges();
    }
}
修改Program.cs（在 builder.Build() 之後）
var app = builder.Build();

// 啟動時自動套用 Migration 並補種子資料
using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    db.Database.Migrate();        // 資料庫不存在就建、有未套用的 Migration 就套用
    SeedData.Initialize(db);
}
為什麼要 CreateScope()？

AddDbContext 註冊的是 Scoped 生命週期—— 「每個 HTTP 請求一個實例」。但啟動的當下還沒有任何請求， 所以要自己開一個範圍才拿得到。

using 讓它用完就釋放。生命週期這件事第 9 章會完整講。

把資料庫刪掉（SSMS 右鍵刪除，或 dotnet ef database drop）， 重新啟動程式——資料庫會自己建好、四種假別自己出現。

啟動時 Migrate() 是教學專案的取捨 好處是「pull 完按 F5 就能跑」，對學習跟小型專案很方便。 正式的多台伺服器環境不會這樣做——會改成部署腳本執行 dotnet ef database update，避免多台機器同時搶著改結構。 完成品專案用的也是啟動時 Migrate，原因相同。

9. 看 EF Core 到底送了什麼 SQL

這是最重要的除錯技巧。 當查詢結果跟你想的不一樣，先看它實際送了什麼。

預設就會印在終端機，只要把記錄層級調低：

修改appsettings.Development.json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",

  }
}

重新啟動、開 /LeaveTypes，終端機會出現：

輸出終端機
info: Microsoft.EntityFrameworkCore.Database.Command[20101]
      Executed DbCommand (3ms) [Parameters=[], CommandType='Text']
      SELECT [l].[Id], [l].[Code], [l].[Description], [l].[IsActive], [l].[Name], [l].[SortOrder]
      FROM [LeaveTypes] AS [l]
      ORDER BY [l].[SortOrder]

.OrderBy(t => t.SortOrder) 真的變成了 ORDER BY。 第 8 章你會用這招抓出效能問題（一個頁面送出幾十句查詢的「N+1 問題」）。

9.1 延遲執行：查詢什麼時候才真的送出去

回想第 1 章提過的延遲執行，在 EF Core 這裡特別重要：

C#還沒送 SQL vs 已經送了
// 這幾行都還沒碰資料庫，只是在「組查詢」
var query = _db.LeaveTypes.Where(t => t.IsActive);
query = query.OrderBy(t => t.SortOrder);

// 這一行才真的送 SQL 出去
var list = await query.ToListAsync();

會觸發查詢的：ToListAsync、FirstOrDefaultAsync、 AnyAsync、CountAsync、SumAsync，以及 foreach。

為什麼這件事重要

因為「在 ToList() 之前」的篩選由資料庫做， 「之後」的由 C# 做。

如果你先 ToListAsync() 把十萬筆全撈回記憶體再 Where， 程式會非常慢——但功能是對的，所以你不會發現。 這是新手最容易寫出的效能地雷。
