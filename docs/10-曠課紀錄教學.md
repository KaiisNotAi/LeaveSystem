## 1. 目標與情境

### 1.1 為什麼要有「曠課紀錄」？

請假流程涵蓋不到一種情境：**學員沒到課、也沒請假**。這時已經是「事後」了，沒有可以被學員自己送出的申請可簽核，只能由行政人員手動登錄一筆。

因此 Phase 6 補上一條**與請假並行但獨立**的資料流：

| 面向 | 請假（Phase 3~5） | 曠課（Phase 6） |
|------|------------------|----------------|
| 誰發起 | 學員 | 行政（Admin/Staff） |
| 需不需要簽核 | 需要（1~3 關） | 不需要 |
| 資料表 | `LeaveRequests` + `LeaveRequestSteps` | `AbsenceRecords`（單張） |
| 狀態機 | Pending → Approved / Rejected / Cancelled | 沒有，登錄即成立 |
| 學員能做什麼 | 送單、查自己的紀錄 | **只能查閱**自己的紀錄，不能新增/編輯 |

### 1.2 三種角色一次看懂

| 角色 | 能做 | 不能做 |
|------|------|--------|
| Student | `/AbsenceRecords` 查自己的曠課；看終身總計 | 新增、修改、刪除任何紀錄；看其他學員 |
| Admin / Staff | `/Admin/AbsenceRecords` 新增、編輯、刪除、依班期/學員/日期篩選 | — |
| 其他角色（Tutor、SectionChief、BranchDirector） | — | 兩條路線都不能進，會被導向 `AccessDenied` |

## 2. 資料模型

### 2.1 AbsenceRecord Entity

```csharp
public class AbsenceRecord
{
	public int Id { get; set; }
	[Required] public int StudentId { get; set; }
	[Required] public DateTime OccurredAt { get; set; }
	[Range(1, 100)] public decimal Hours { get; set; }
	[StringLength(500)] public string? Note { get; set; }
	[Required] public int CreatedByUserId { get; set; }
	public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

	public UserAccount Student { get; set; } = null!;
	public UserAccount CreatedByUser { get; set; } = null!;
}
```

| 欄位 | 說明 |
|------|------|
| `StudentId` | 學員（會被 Service 二次驗證必為 Student 角色） |
| `OccurredAt` | 曠課發生時間，含日期與上課時段的開始時間 |
| `Hours` | `decimal(6,2)`；`[Range(1, 100)]` 加 ViewModel 的整數檢查一起把關 |
| `Note` | 選填備註；Service 會把「全空白」統一存成 `null` |
| `CreatedByUserId` | 登錄者（行政），**Update 不覆寫** |
| `CreatedAt` | 一律以 `DateTime.UtcNow` 寫入，**Update 不覆寫** |

### 2.2 為什麼稽核欄位在 Update 時不能覆寫？

`CreatedByUserId` 與 `CreatedAt` 只回答一個問題：**這筆紀錄「第一次」是誰在什麼時候登進來的？** 如果 Update 時把它們也一併改掉，日後想追究「這筆紀錄何時被建立」就永遠回不到原點。

因此 `AbsenceRecordService.UpdateAsync` 只更新業務欄位（`StudentId` / `OccurredAt` / `Hours` / `Note`），稽核欄位保留：

```csharp
record.StudentId = input.StudentId;
record.OccurredAt = input.OccurredAt;
record.Hours = input.Hours;
record.Note = NormalizeNote(input.Note);
// CreatedByUserId / CreatedAt 刻意不動
```

## 3. 分層走一次（Controller → Service → EF Core）

一個 HTTP 請求進入 Phase 6 功能時會經過的層次：

```
[瀏覽器]
   │  GET /Admin/AbsenceRecords?CohortId=1&DateFrom=2026-06-01&DateTo=2026-06-30
   ▼
[UseAuthentication] 讀 Cookie → 還原 User
   ▼
[UseAuthorization] 檢查 [Authorize(Roles="Admin,Staff")]
   ▼
[Admin.AbsenceRecordsController.Index(query)]
   │  只做「呼叫 Service → 回 View」，不寫 LINQ
   ▼
[AbsenceRecordService.GetForAdminAsync(query)]
   │  動態組 WHERE、補 DateTo、排序、投影成 ViewModel、算 TotalHours、載入下拉
   ▼
[EF Core] 產生 SQL → SQL Server
   ▼
[Razor] Views/Admin/AbsenceRecords/Index.cshtml 綁定 AbsenceRecordAdminViewModel
```

要記住的分工原則：

- **Controller 保持薄層**：只負責「取 UserId → 呼叫 Service → 回 View」。
- **Service 承擔業務規則**：包含資料所有權（`GetMineAsync` 強制 `studentId`）、驗證（`IsValidStudentAsync`）、正規化（`NormalizeNote` / `NormalizeDateTo`）。
- **ViewModel 承擔表單驗證**：`[Required]` / `[Range]` / `IValidatableObject` 全在 ViewModel 上。

## 4. 兩個同名 Controller 的分流

Phase 6 有兩個 `AbsenceRecordsController`：

| 位置 | 路由 | 授權 | 動作 |
|------|------|------|------|
| `Controllers/AbsenceRecordsController.cs` | `/AbsenceRecords` | Student | `Index`（自查列表） |
| `Controllers/Admin/AbsenceRecordsController.cs` | `/Admin/AbsenceRecords/*` | Admin, Staff | `Index` / `Create` / `Edit` / `Delete` |

### 4.1 View 路徑分流的陷阱

`Program.cs` 為了行政後台把 `/Views/Admin/{1}/{0}.cshtml` **插入到 `ViewLocationFormats` 最前面**：

```csharp
options.ViewLocationFormats.Insert(0, "/Views/Admin/{1}/{0}.cshtml");
```

好處：`Controllers/Admin/XxxController` 的 View 可以放在 `Views/Admin/Xxx/`。

副作用：學員版 Controller 的 `return View(vm)` **也會先找** `Views/Admin/AbsenceRecords/Index.cshtml`，命中的話會拿 `AbsenceRecordAdminViewModel` 去綁 `MyAbsenceRecordViewModel`，直接壞掉。

### 4.2 正確做法：絕對路徑

學員版 Controller 顯式指定 View：

```csharp
return View("~/Views/AbsenceRecords/Index.cshtml", vm);
```

未來如果再遇到「同名 Controller 分兩區」的情況，記得沿用這個寫法。

## 5. Service 邏輯重點

`AbsenceRecordService` 是本 Phase 的商業邏輯核心，六個 public 方法對應六個場景：

| 方法 | 場景 |
|------|------|
| `CreateAsync` | 行政新增 |
| `UpdateAsync` | 行政編輯 |
| `DeleteAsync` | 行政刪除 |
| `GetForAdminAsync` | 行政清單頁（含篩選 + 下拉 + 總計） |
| `GetMineAsync` | 學員自查（強制 `studentId`） |
| `GetForEditAsync` | 行政載入編輯表單 |

### 5.1 `IsValidStudentAsync`：Student 角色雙保險

即使前端下拉只列 Student，也不能相信 POST 進來的 `StudentId`。Service 用一條 LINQ 驗證：

```csharp
_db.UserAccounts.AnyAsync(u => u.Id == userId
	&& u.UserRoles.Any(ur => ur.Role.Name == "Student"));
```

`CreateAsync` / `UpdateAsync` 一開頭就檢查，不通過直接回 `AbsenceRecordActionResult(false, "找不到指定的學員…")`。

### 5.2 `NormalizeNote`：空白正規化

```csharp
private static string? NormalizeNote(string? note)
	=> string.IsNullOrWhiteSpace(note) ? null : note.Trim();
```

理由：`""` / `"   "` / `null` 三種都應該視為「沒填備註」，資料庫存 `null` 最乾淨，也讓 UI 顯示邏輯統一。

### 5.3 `NormalizeDateTo`：日期迄補到當日底

`<input type="date">` 送出的時間只到「當天 00:00:00」，如果直接 `a.OccurredAt <= DateTo` 會漏掉當天 00:00 之後的紀錄。

```csharp
private static DateTime NormalizeDateTo(DateTime dateTo)
	=> dateTo.TimeOfDay == TimeSpan.Zero
		? dateTo.Date.AddDays(1).AddTicks(-1)  // 23:59:59.9999999
		: dateTo;
```

這與 Phase 5 `LeaveReportService.GetAdminReportAsync` 的處理完全一致，兩處未來要一起改。

### 5.4 `GetMineAsync`：兩個關鍵設計

```csharp
var q = _db.AbsenceRecords.AsNoTracking()
	.Where(a => a.StudentId == studentId);  // ← 主 WHERE，安全性關鍵
// ... 套用日期篩選 ...
var items = await q.OrderByDescending(a => a.OccurredAt).Select(...).ToListAsync();

// 終身總計：刻意不套日期篩選
var totalHours = await _db.AbsenceRecords.AsNoTracking()
	.Where(a => a.StudentId == studentId)
	.SumAsync(a => (decimal?)a.Hours) ?? 0m;
```

- **主 WHERE 一定要以 `studentId` 為條件**：即使 `query` 內容被竄改，也讀不到別的學員資料。
- **`TotalHours` 是「終身總計」**：不套 `DateFrom` / `DateTo`。設計目的是讓學員每次進頁面都能看到一個穩定的自我警惕數字，不會因為只看「6 月」就以為自己曠課少。

### 5.5 兩層下拉（班期 → 學員）：UX 優化的選型理由

情境：班期可能 > 15，每班 30~40 人。單一學員下拉一旦到上百項就遠不如「先選班期縮範圍」好挑。但「兩層」的實作方式有好幾種，本專案選了**一次載入全部學員 + 前端 JS 依 `data-cohort-id` 過濾**，而不是 AJAX 或第三方套件。

#### 為什麼不用 AJAX？

就算情境達到上限（例 `20 班 × 40 人 = 800 人`），回傳的 JSON （Id/DisplayName/Username/CohortId）仍小於 60 KB；實實在在比一張圖還小。多一個 AJAX endpoint 的成本（權限、防偽 token、序列化、教學重點多一個 REST 概念）大於收益。

#### 為什麼「班期」下拉不 POST？

因為它只是前端的 UX 輔助。伺服器只需要知道行政最終選中的是哪一位 `StudentId`。班期選單在 View 上只給 `id`、不給 `name` 也不用 `asp-for`：

```html
<label for="CohortFilter" class="form-label">班期</label>
<select id="CohortFilter" class="form-select">
    <option value="">— 全部班期 —</option>
    @foreach (var c in Model.CohortOptions)
    {
        <option value="@c.Id">@c.Name</option>
    }
</select>
```

好處：後端 `AbsenceRecordCreateInput` 不需新增任何 Bind 欄位，既有 Service / Controller 契約不變，測試不用重寫。

#### 學員 `<option>` 掋 `data-cohort-id`

```html
<select asp-for="StudentId" class="form-select">
    <option value="">— 請選擇學員 —</option>
    @foreach (var s in Model.StudentOptions)
    {
        <option value="@s.Id" data-cohort-id="@s.CohortId">@s.DisplayName（@s.Username）</option>
    }
</select>
```

前端 JS 只做一件事：班期一改變，把不同班的 `option` 的 `hidden` 屬性設為 `true`。完整範例見 [Views/Admin/AbsenceRecords/Create.cshtml](../Views/Admin/AbsenceRecords/Create.cshtml) 頁尾的 `<script>` 區塊。

#### Edit 頁多一個「進場反推」步驟

Edit 載入時已知 `StudentId`，但「班期」下拉還是「全部班期」。進場時讓 JS 反推：讀目前選中的 `<option>` 的 `data-cohort-id`，回填到班期下拉。這樣行政一進頁就看到 A 班已預選、學員下拉只顯示 A 班的名字。

```javascript
const selectedOption = studentSel.options[studentSel.selectedIndex];
if (selectedOption && selectedOption.value) {
    const preselectCohort = selectedOption.getAttribute('data-cohort-id') || '';
    if (preselectCohort) cohortSel.value = preselectCohort;
}
```

#### Progressive Enhancement：停用 JS 不會壞事

如果使用者停用 JS，班期下拉不會過濾，但學員下拉仍完整顯示全部選項（退化成兩層下拉之前的 Phase 6 行為），送出仍能正常建立紀錄。這是「優化但不依賴」的前端強化原則。

### 5.6 Student 有效性檢查升級：兩層規則合一

Phase 6 上線初期的 `IsValidStudentAsync` 只問一件事：存不存在且具 Student 角色？兩層下拉上線後多了一條正式規則：**未指派班期的學員不可登錄曠課**。這條規則必須在 Service 層把關，而不只靠 UI，否則行政直接 POST 一個未歸班的 `StudentId` 就能繞過。

重構後的 `CheckStudentAsync` 回傳的不再是 `bool`，而是 `string?`：

```csharp
private async Task<string?> CheckStudentAsync(int userId)
{
    var info = await _db.UserAccounts.AsNoTracking()
        .Where(u => u.Id == userId
            && u.UserRoles.Any(ur => ur.Role.Name == RoleNameStudent))
        .Select(u => new { u.CohortId })
        .FirstOrDefaultAsync();

    if (info is null) return ErrorStudentNotFound;      // 不存在或不是 Student
    if (info.CohortId is null) return ErrorStudentNoCohort;  // 未指派班期
    return null; // 通過
}
```

好處：兩種失敗情境回專屬錯誤訊息，行政看到的 UI 提示能直接讓他知道要修什麼。相對的，`GetStudentOptionsAsync` 也同步加上 `u.CohortId != null` 過濾，避免 UI 一開始就列出未歸班學員讓行政從選埔到才报錯。UI 擋 + Service 擋，雙保險。

## 6. 行政操作步驟

前置：先用 Admin/Staff 帳號登入。若沒有 Staff，先到 `/Admin/Users` 建一個。

### 6.1 進入曠課紀錄管理

- 上方導覽列 → `行政後台` → `曠課紀錄管理`
- 或直接開網址 `/Admin/AbsenceRecords`

### 6.2 新增一筆曠課紀錄

1. 按右上角 `＋ 新增曠課紀錄`。
2. 填寫表單：

   | 欄位 | 說明 |
   |------|------|
   | 班期 | 下拉選單（UX 輔助欄位，不會 POST）。選定時下方學員下拉只顯示該班學員；選「全部班期」就可以看到所有已歸班學員 |
   | 學員 | 下拉選單，只列**已指派班期且具 Student 角色的使用者**（含停用者，方便補登歷史紀錄）。未指派班期的學員根本不會出現在這裡 |
   | 發生時間 | `datetime-local` 選擇器；預設「今天 08:00」 |
   | 曠課時數 | 1~100 整數；輸入 1.5 或 0 會被擋 |
   | 備註 | 選填，最長 500 字；全空白會被存成 `null` |

3. 送出後：
   - 成功 → 導向 `/Admin/AbsenceRecords`，畫面上方跳綠色訊息「已新增曠課紀錄」。
   - 失敗（例如直接 POST 了未指派班期的 StudentId）→ 停留在表單，欄位下方顯示錯誤訊息（Phase 6 規則）。

### 6.3 篩選查詢

清單頁上方是 GET 表單：

| 條件 | 說明 |
|------|------|
| 班期 | 依學員的 `CohortId` 過濾；未指派班期的學員不會被班期條件收錄 |
| 學員 | 精準到單一學員 |
| 日期起 / 日期迄 | 比對 `AbsenceRecord.OccurredAt`；日期迄含當天 |

- 按 `查詢` 送出，結果表格會過濾，底部總計會隨條件變動。
- 按 `清除條件` 一次清光所有篩選。
- 條件保留在 URL 上，可貼給同事直接看到相同結果。

### 6.4 編輯與刪除

- **編輯**：清單列右側 `編輯` → 修改後儲存；稽核欄位（登錄者、登錄時間）不會被覆寫。
- **刪除**：清單列右側 `刪除` → 瀏覽器 `confirm()` 二次確認 → 成功後綠訊，失敗（例如 Id 已不存在）紅訊。

## 7. 學員查詢步驟

前置：用一個具 Student 角色的帳號登入。

1. 導覽列 → `我的曠課紀錄`（或直接 `/AbsenceRecords`）。
2. 頁面最上方是「截至目前累計曠課時數」卡片，就是 §5.4 的 `TotalHours`（終身總計）。
3. 中間是 GET 篩選表單，只有 `日期起` / `日期迄` 兩個欄位（沒有學員維度，因為 Service 只回自己的紀錄）。
4. 下方是結果表格，欄位比行政版精簡：只有發生時間、時數、備註、登錄時間；**刻意不顯示登錄者**，那是內部審計資訊。

若學員認為紀錄有誤，畫面底部有一行提示：「請聯繫行政人員協助修正」，因為學員無法自行編輯。

### 8.1 測試資料速查表（`AbsenceRecordTestScenario`）

| 常數 | 值 | 說明 |
|------|-----|------|
| `CohortIdA` / `CohortIdB` | 1 / 2 | 兩個班期 |
| `StudentUserIdA` / `StudentUserIdB` | 100 / 101 | 兩位學員（小明 / 小華） |
| `UnassignedStudentUserId` | 102 | 小陳：有 Student 角色但 `CohortId = null`（專門驗證 §5.6 規則） |
| `StaffUserId` | 200 | 行政人員（登錄者） |
| `OutsiderUserId` | 999 | 未指派任何角色的路人（用來驗 Service 角色檢查） |

種子的 4 筆已存在紀錄：

| 代號 | 學員 | 時間 | 時數 | 備註 |
|------|------|------|------|------|
| A1 | 小明 | 2026-06-08 08:00 | 2h | 遲到過早 |
| A2 | 小明 | 2026-06-15 13:00 | 4h | 下午未到 |
| A3 | 小明 | 2026-07-10 08:00 | 1h | (null) |
| B1 | 小華 | 2026-06-20 08:00 | 8h | 整天未到 |

快速驗證用：

- 小明終身總計 = 7h（A1+A2+A3），小華終身總計 = 8h（B1），全部 = 15h（4 筆）。
- 6 月篩選：A1+A2+B1 = 14h（3 筆）。
- CohortId=A 篩選：A1+A2+A3 = 7h（3 筆）。

### 8.2 七個測試群組對照

| 群組 | 測試意圖 |
|------|---------|
| 1. Create | 合法輸入、找不到學員、非 Student 角色、Note 全空白轉 null |
| 2. Update | 合法更新、稽核欄位不變、找不到紀錄回失敗 |
| 3. Delete | 存在時刪成功 |
| 4. GetForAdmin | 無篩選 + 排序、CohortId 篩選、StudentId 篩選、DateTo 補當天 |

## 9. 手動驗收清單

## 10. 常見問題

### Q1：新增曠課時輸入 `1.5`，前端沒擋，送出後才顯示錯誤？

`<input type="number" step="1">` 在瀏覽器層雖然有提示，但**不同瀏覽器實作不一**（有些會四捨五入、有些放行）。真正把關的是 ViewModel 的 `IValidatableObject.Validate`：

```csharp
if (Hours != Math.Floor(Hours))
	yield return new ValidationResult("曠課時數必須為正整數（不接受小數）", new[] { nameof(Hours) });
```

伺服器端才是安全網，前端 `step="1"` 只是使用者體驗。

### Q2：學員自查頁面壞掉，顯示模型型別錯誤？

八成是有人把 `Controllers/AbsenceRecordsController.cs` 的 `View(...)` 改成 `return View(vm);`，命中了 `Views/Admin/AbsenceRecords/Index.cshtml`。修回：

```csharp
return View("~/Views/AbsenceRecords/Index.cshtml", vm);
```

原因見 §4.1。

### Q3：新增曠課時明明選了 Student，還是被說「找不到指定的學員」或「尚未指派班期」？

兩種情境：

- **「找不到指定的學員」**：帳號不存在、或途中被刪除、或沒有 Student 角色。到 `/Admin/Users` 確認帳號、補上 Student 角色即可。
- **「尚未指派班期」**：Phase 6 規則：未歸班的學員不能登錄曠課（見 §5.6）。到 `/Admin/Users` 編輯帳號，將 CohortId 指派到對應班期，或到 `/Admin/Cohorts` 對應班期把學員拉進來。

手動登錄前沒看到這兩條錯誤？那並非不正常——兩層下拉已經先過濾了未歸班的學員，行政從下拉選不到就不會遇到。但若行政直接用工具 POST（例如 Postman）就會看到 Service 層錯誤訊息。

### Q4：明明 6/30 有一筆 20:00 的紀錄，日期迄選 `6/30` 卻查不到？

代表 `NormalizeDateTo` 沒生效。檢查：

- `AbsenceRecordAdminQuery.DateTo` 型別是 `DateTime?`。
- `AbsenceRecordService.GetForAdminAsync` 內走 `NormalizeDateTo(query.DateTo.Value)` 分支。
- 用 SQL Profiler 或 EF Core Log 看實際送的 WHERE，確認尾巴是 `23:59:59.9999999`。

### Q5：學員終身總計為什麼不會隨日期篩選變？

那是**故意的設計**。如果隨著日期變動，學員只要選一段「乾淨」的區間就會看到 0，會失去自我警惕的作用。若日後真的要提供「這段區間累計」，另外加一個欄位（例如 `RangeHours`）並保留 `TotalHours` 語意。

### Q6：新增頁面「班期」下拉是空的、或學員下拉是空的？

兩種情境都會在表單上方跳黃色提示：

- **班期下拉空**：代表系統完全沒班期，需先到 `/Admin/Cohorts` 新增至少一個班期。
- **學員下拉空**：代表現在沒任何「已指派班期的 Student」。先到 `/Admin/Users` 建立 Student 帳號，再到 `/Admin/Cohorts` 對應班期把他們拉進來（或在 `/Admin/Users` 編輯頁直接選 CohortId）。

這樣的設計拉手行政把前置作業先做完，避免在登錄時才發現基礎資料不齊全。

### Q7：停用瀏覽器 JavaScript 時兩層下拉還能用嗎？

能使用但不會過濾。班期下拉還在，但改班期時學員下拉不會進行過濾——退化回「單一學員下拉」行為。這是 Progressive Enhancement：JS 只是優化 UX，後端驗證（`CheckStudentAsync`）才是正確性的把關。
