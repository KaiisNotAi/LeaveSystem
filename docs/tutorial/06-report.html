紀錄查詢與時數統計

ReportsController 有三個查詢 Action，全部轉給同一個 LeaveReportService。這條流程的重點不在「怎麼查」，而在兩個決策： 哪些資料在資料庫端過濾、哪些拉回記憶體再算， 以及學員與行政的權限怎麼在同一個 Controller 裡分流。

為什麼 Controller 上只掛 [Authorize]，角色寫在每個 Action
ReportsController.cs:24 的 [Authorize] 只要求「必須登入」， 因為同一個 Controller 裡學員與行政各有各的 Action。 若把角色寫在 class 上，就得拆成兩個 Controller。

程式碼對照

1 GET /Reports/Summary Views/Reports/Summary.cshtml

純 GET，沒有查詢字串。「我是誰」完全靠 Cookie， 網址上不帶 studentId——這樣就沒有「改網址看別人資料」的破口。

2 [Authorize(Roles = "Student")] Summary() ReportsController.cs:72–74

使用者 Id 從 ClaimTypes.NameIdentifier 取得 （02 認證第 9 步寫進去的那筆 Claim）， 再往下傳給 Service。 

[HttpGet]

3 GetMyLeaveTypeSummaryAsync(int studentId) Services/LeaveReportService.cs:96

參數只有 studentId，沒有任何篩選條件—— 累計時數是「終身總計」，不隨畫面上的日期篩選改變。 這跟 /Reports 的清單查詢是兩種不同語意。 

public async Task<MyLeaveSummaryViewModel> GetMyLeaveTypeSummaryAsync(int studentId)
4 _db.UserAccounts.AsNoTracking().Include(u => u.Cohort).FirstOrDefaultAsync(…) Services/LeaveReportService.cs:99–102

AsNoTracking()：這是唯讀查詢， 不需要 EF Core 建立變更追蹤快照，省記憶體也省時間。 整個 LeaveReportService 的查詢都加了它。 Cohort 可能是 null（學員還沒被指派班期），所以後面全用 ?. 存取。 

// 先取學員（含班期），Cohort 可能為 null（尚未指派班期）
var student = await _db.UserAccounts
    .AsNoTracking()
    .Include(u => u.Cohort)
    .FirstOrDefaultAsync(u => u.Id == studentId);
5 .Where(r => r.StudentId == studentId && r.Status == Approved).ToListAsync() Services/LeaveReportService.cs:106–110

篩選在資料庫端做（WHERE 進得了 SQL）， 但 ToListAsync() 之後就把資料拉回記憶體了。 這是刻意的——原因見下一步。 

// 只累計 Approved（與 Phase 3 班期上限口徑一致）
// 撈完整實體到記憶體，方便同時做 group + 依 LeaveType.SortOrder 排序
var approved = await _db.LeaveRequests
    .AsNoTracking()
    .Include(r => r.LeaveType)
    .Where(r => r.StudentId == studentId && r.Status == LeaveStatus.Approved)
    .ToListAsync();
6 → List<LeaveRequest>（每筆都帶著 LeaveType） Services/LeaveReportService.cs:110

Include(r => r.LeaveType) 讓假別的 Name 與 SortOrder 一起被載入。若少了它，下一步在記憶體端存取 r.LeaveType.Name 會因為沒有延遲載入而丟 NullReferenceException。

7 approved.GroupBy(…).OrderBy(SortOrder).Select(…) Services/LeaveReportService.cs:112–122

這一段是 LINQ to Objects，不是 LINQ to Entities。 因為前一步已經 ToListAsync()，這裡就跑在記憶體裡。 這麼做的理由寫在原始碼註解裡：GroupBy 在不同資料庫 provider 的翻譯行為有差異（尤其還要同時依 LeaveType.SortOrder 排序）， 拉回來算比較可預測——單一學員的假單量本來就不大。 

var items = approved
    .GroupBy(r => new { r.LeaveTypeId, r.LeaveType.Name, r.LeaveType.SortOrder })
    .OrderBy(g => g.Key.SortOrder)
    .ThenBy(g => g.Key.LeaveTypeId)
    .Select(g => new MyLeaveTypeSummaryItem
    {
        LeaveTypeName = g.Key.Name,
        TotalHours    = g.Sum(r => r.TotalHours),
        RequestCount  = g.Count()
    })
    .ToList();
什麼時候不該這樣做
GetAdminReportAsync（:134）用了同樣的手法， 但它的資料量是整個班期。目前規模沒問題， 若學員數成長到數千人，就該把彙總改寫成資料庫端的 GROUP BY， 或改用資料庫檢視表。
8 → MyLeaveSummaryViewModel Services/LeaveReportService.cs:124–130

Service 回傳的是 ViewModel 而不是 Entity。 View 拿到的只有它需要顯示的欄位， 不會不小心把 PasswordHash 這類東西一起帶到畫面上。 CohortLeaveLimitHours 為 null 時，View 就不畫進度條。 

return new MyLeaveSummaryViewModel
{
    Items                 = items,
    TotalApprovedHours    = items.Sum(i => i.TotalHours),
    CohortLeaveLimitHours = student?.Cohort?.LeaveLimitHours,   // 沒班期就是 null
    CohortName            = student?.Cohort?.Name
};
9 return View(vm) Views/Reports/Summary.cshtml

進度條的百分比 = TotalApprovedHours / CohortLeaveLimitHours。 這個上限值就是送單時第 5 步拿來擋人的同一個數字， 學員因此能事先知道自己還剩多少額度，而不是送出去才被退。

自己動手驗證

  1. 在 LeaveReportService.cs:112（GroupBy 那行）設中斷點， 觀察 approved 已經是一個 List——證明後面都在記憶體算。
  2. 用 /Reports 篩「已核准」與「進行中」，比對 /Reports/Summary 的總計—— 只有已核准的會被算進去。
  3. 在 Output 視窗看 EF Core 送出的 SQL：Summary 只送兩句查詢， 沒有 GROUP BY。
  4. 把某位學員的 CohortId 清成 null，開 /Reports/Summary—— 明細照常顯示，但進度條消失（CohortLeaveLimitHours == null）。
  5. 用學員帳號直接開 /Reports/Admin，看它被導到 /Account/AccessDenied。
