1. 先想清楚：誰跟誰有關係

在寫任何程式碼之前，先把關係用白話講一遍：

關係類型白話
班期 ↔ 學員 一對多 一個班期有很多學員；一個學員只屬於一個班期
使用者 ↔ 角色 多對多 一個人可以同時是導師和行政；一個角色也有很多人
班期 ↔ 導師 / 科長 / 分署長 特殊 一個班期各指定一位。這三個都指向使用者表
關係想錯，後面全部要重來 資料模型是整個系統的地基。寫程式之前先在紙上畫一遍， 問自己「這邊可以有幾個？那邊可以有幾個？」。 完成品專案的完整關係圖在 專題報告的 ER 圖，可以先去看一眼。

2. 一對多：班期與學員

一對多的寫法有固定套路：「多」的那邊放外鍵，兩邊各放一個導覽屬性。

新增檔案Models/Entities/Cohort.cs
using System.ComponentModel.DataAnnotations;

namespace MyLeaveSystem.Models.Entities;

public class Cohort
{
    public int Id { get; set; }

    [Required, MaxLength(50)]
    public string Name { get; set; } = string.Empty;

    public DateTime StartDate { get; set; }
    public DateTime EndDate   { get; set; }

    // 總上課時數，例如 900
    public int TotalHours { get; set; }

    // 請假上限百分比，預設 10%
    public int LeaveLimitPercent { get; set; } = 10;

    // 計算屬性：不存資料庫（第 1 章講過的單一真相來源）
    public int LeaveLimitHours => (int)Math.Floor(TotalHours * LeaveLimitPercent / 100.0);

    // 導覽屬性：這個班期底下的所有學員
    public ICollection<UserAccount> Students { get; set; } = new List<UserAccount>();
}
新增檔案Models/Entities/UserAccount.cs
using System.ComponentModel.DataAnnotations;

namespace MyLeaveSystem.Models.Entities;

public class UserAccount
{
    public int Id { get; set; }

    [Required, MaxLength(50)]
    public string Username { get; set; } = string.Empty;

    [Required, MaxLength(100)]
    public string DisplayName { get; set; } = string.Empty;

    // 第 10 章才會真的用到，先留欄位
    [Required, MaxLength(100)]
    public string PasswordHash { get; set; } = string.Empty;

    [MaxLength(100)]
    public string? Email { get; set; }

    public bool IsActive { get; set; } = true;

    // ── 一對多的「多」這一端 ──
    // 外鍵。int? 代表可以沒有班期（老師、行政人員就沒有）
    public int? CohortId { get; set; }

    // 導覽屬性：指回那個班期
    public Cohort? Cohort { get; set; }
}
外鍵 CohortId 與導覽屬性 Cohort，為什麼兩個都要？

CohortId（int?）是資料庫實際存的東西， 也是你在表單下拉選單裡會用到的值。

Cohort（物件）是給 C# 用的方便寫法， 讓你能寫 student.Cohort.Name 而不用自己再查一次。

重點：Cohort 這個屬性預設是 null， 除非你明確用 Include 把它載進來。 這是第 6 節的主題，也是新手最常撞的 NullReferenceException 來源。

EF Core 怎麼知道它們是一對？ 靠命名慣例：屬性叫 Cohort（型別是 Cohort）， 旁邊剛好有個 CohortId——「導覽屬性名 + Id」就是它的外鍵。 名字不照慣例的話要用 [ForeignKey] 屬性明講。

多對多沒辦法用兩張表表示（一個欄位存不下多個值）， 必須加一張中間表把它拆成兩個一對多：

= null!; 是什麼意思？ 那個驚嘆號是在跟編譯器說「我知道它現在是 null，但你別念我，執行時 EF Core 會填好」。 必填的導覽屬性用 null!，選填的用 ?—— 對照一下 UserRole.User（必填，用 null!） 與 UserAccount.Cohort（選填，用 ?）。

4. 難題：班期上的三個簽核人

班期要指定導師、科長、分署長各一位，三個都指向 UserAccount。 這裡有個坑：EF Core 會搞不清楚 Cohort.Students 跟這三個的關係。

修改Models/Entities/Cohort.cs
    public ICollection<UserAccount> Students { get; set; } = new List<UserAccount>();

    // ── 三位簽核人（都可以先不指派）──
    public int? TutorUserId          { get; set; }
    public int? SectionChiefUserId   { get; set; }
    public int? BranchDirectorUserId { get; set; }

    public UserAccount? Tutor          { get; set; }
    public UserAccount? SectionChief   { get; set; }
    public UserAccount? BranchDirector { get; set; }
}

現在有四條路徑從 Cohort 通往 UserAccount， EF Core 猜不出誰配誰。必須在 AppDbContext 裡明確講清楚：

修改Data/AppDbContext.cs
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Models.Entities;

namespace MyLeaveSystem.Data;

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<LeaveType>   LeaveTypes   => Set<LeaveType>();
    public DbSet<UserAccount> UserAccounts => Set<UserAccount>();
    public DbSet<Role>        Roles        => Set<Role>();
    public DbSet<UserRole>    UserRoles    => Set<UserRole>();
    public DbSet<Cohort>      Cohorts      => Set<Cohort>();

    // 慣例猜不到的關係，在這裡明確設定
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // ① 中間表用複合主鍵
        modelBuilder.Entity<UserRole>()
            .HasKey(ur => new { ur.UserId, ur.RoleId });

        // ② 帳號不可重複
        modelBuilder.Entity<UserAccount>()
            .HasIndex(u => u.Username)
            .IsUnique();

        // ③ 學員 ↔ 班期（一對多）
        modelBuilder.Entity<UserAccount>()
            .HasOne(u => u.Cohort)
            .WithMany(c => c.Students)
            .HasForeignKey(u => u.CohortId)
            .OnDelete(DeleteBehavior.Restrict);

        // ④ 三位簽核人：WithMany() 空的＝對面不需要導覽屬性
        modelBuilder.Entity<Cohort>()
            .HasOne(c => c.Tutor).WithMany()
            .HasForeignKey(c => c.TutorUserId)
            .OnDelete(DeleteBehavior.Restrict);

        modelBuilder.Entity<Cohort>()
            .HasOne(c => c.SectionChief).WithMany()
            .HasForeignKey(c => c.SectionChiefUserId)
            .OnDelete(DeleteBehavior.Restrict);

        modelBuilder.Entity<Cohort>()
            .HasOne(c => c.BranchDirector).WithMany()
            .HasForeignKey(c => c.BranchDirectorUserId)
            .OnDelete(DeleteBehavior.Restrict);
    }
}
OnDelete(DeleteBehavior.Restrict) 是什麼？

預設行為是連鎖刪除：刪掉一個班期，底下所有學員跟著被刪。 這在請假系統是災難。

Restrict 的意思是「底下還有東西就不准刪」， 資料庫會直接拒絕。這樣你就不會不小心因為刪一個班期， 連帶弄丟一整批學員與他們的請假紀錄。

另外，多條路徑指向同一張表時，SQL Server 也會拒絕多重連鎖刪除路徑 （報錯 may cause cycles or multiple cascade paths）—— 所以這裡不設 Restrict 的話，Migration 根本跑不起來。

6. Include：載入關聯資料

這是本章最重要的一節。先撞牆：

C#這段會爆炸
var users = await _db.UserAccounts.ToListAsync();

foreach (var u in users)
{
    // 💥 NullReferenceException：u.Cohort 是 null
    Console.WriteLine($"{u.DisplayName} 屬於 {u.Cohort.Name}");
}
為什麼是 null？資料庫裡明明有 CohortId

因為 EF Core 不會自動去載入關聯物件。 u.CohortId 有值（那是同一張表的欄位）， 但 u.Cohort 是另一張表的資料，你沒開口要，它就不撈。

這是刻意的設計：如果每次查使用者都自動把班期、角色、請假單全部撈出來， 一個簡單查詢會變成災難。

正確做法是明確要求：

C#Include 的三種用法
// ① 載入一層
var users = await _db.UserAccounts
    .Include(u => u.Cohort)
    .ToListAsync();

// ② 載入多層：先 Include 再 ThenInclude
//    使用者 → 他的 UserRoles → 每個 UserRole 的 Role
var withRoles = await _db.UserAccounts
    .Include(u => u.UserRoles)
        .ThenInclude(ur => ur.Role)
    .ToListAsync();

// ③ 同時載入好幾條分支：Include 好幾次
var full = await _db.UserAccounts
    .Include(u => u.Cohort)
    .Include(u => u.UserRoles).ThenInclude(ur => ur.Role)
    .ToListAsync();

using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Data;

namespace MyLeaveSystem.Controllers;

public class UsersController : Controller
{
    private readonly AppDbContext _db;
    public UsersController(AppDbContext db) => _db = db;

    public async Task<IActionResult> Index()
    {
        var users = await _db.UserAccounts
            .AsNoTracking()
            .Include(u => u.Cohort)                              // 班期
            .Include(u => u.UserRoles).ThenInclude(ur => ur.Role) // 角色
            .OrderBy(u => u.Username)
            .ToListAsync();

        return View(users);
    }
}

7. N+1 問題

這是所有 ORM 最經典的效能陷阱。假設你在迴圈裡查資料：

C#❌ 錯誤示範
var users = await _db.UserAccounts.ToListAsync();          // 1 次查詢

foreach (var u in users)
{
    // 每一圈都查一次資料庫！100 個使用者 = 100 次查詢
    var cohort = await _db.Cohorts.FirstOrDefaultAsync(c => c.Id == u.CohortId);
    Console.WriteLine($"{u.DisplayName} — {cohort?.Name}");
}

總共 1 + N 次查詢，所以叫 N+1。 測試時只有 3 筆資料，你完全感覺不到；上線之後有 500 個使用者，這一頁就要跑五百多次往返。

C#✅ 正確做法
// 用 Include：EF Core 會用 JOIN 一次撈完
var users = await _db.UserAccounts
    .Include(u => u.Cohort)
    .ToListAsync();

foreach (var u in users)
{
    Console.WriteLine($"{u.DisplayName} — {u.Cohort?.Name}");   // 不會再查資料庫
}

7.1 Include 沒辦法解決的時候：批次查詢

有時候你要的東西不是導覽屬性，而是一個統計值。 例如待簽核清單每一列都要顯示「這位學員已請幾小時」：

C#改寫自完成品：Services/ApprovalService.cs:283-290
// ❌ N+1：迴圈裡逐一 SumAsync
foreach (var item in pendingList)
{
    item.UsedHours = await _db.LeaveRequests
        .Where(r => r.StudentId == item.StudentId && r.Status == Approved)
        .SumAsync(r => r.TotalHours);
}

// ✅ 一次撈完再查字典
var studentIds = pendingList.Select(x => x.StudentId).Distinct().ToList();

var usedByStudent = await _db.LeaveRequests
    .Where(r => studentIds.Contains(r.StudentId) && r.Status == Approved)
    .GroupBy(r => r.StudentId)
    .Select(g => new { StudentId = g.Key, Sum = g.Sum(r => r.TotalHours) })
    .ToDictionaryAsync(x => x.StudentId, x => x.Sum);

foreach (var item in pendingList)
{
    item.UsedHours = usedByStudent.TryGetValue(item.StudentId, out var s) ? s : 0m;
}
怎麼發現自己寫出 N+1

打開 SQL 記錄（第 6 章第 9 節）， 開一次頁面，數終端機印出幾句 SELECT。

一個清單頁應該只有個位數的查詢。 如果你看到幾十句長得幾乎一樣的 SELECT，就是 N+1。

8. 投影：只拿你要的欄位

Include 會把整個關聯物件的所有欄位撈回來。 如果你只需要一個名字，可以用 Select 只挑要的：

C#投影查詢
var rows = await _db.UserAccounts
    .AsNoTracking()
    .Select(u => new
    {
        u.Username,
        u.DisplayName,
        CohortName = u.Cohort!.Name      // EF Core 會自動 JOIN
    })
    .ToListAsync();

產生的 SQL 只會 SELECT 那三個欄位，而不是兩張表的全部欄位。

什麼時候用 Include、什麼時候用 Select

Include：你需要完整的物件（例如要拿去修改，或是後面邏輯會用到很多欄位）。

Select 投影：純顯示用的清單、報表。資料量大時差別很明顯。

完成品專案兩種都有用：ApprovalService.LoadStepForActionAsync 用 Include（要拿去改）， AbsenceRecordService.CheckStudentAsync 用 .Select(u => new { u.CohortId })（只要一個欄位）。
