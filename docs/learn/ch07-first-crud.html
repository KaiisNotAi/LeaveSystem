2. Edit：兩個 Action 的第二種樣貌

Edit 跟 Create 的骨架幾乎一樣，只差兩件事： GET 時要先把現有資料填進表單， POST 時要知道在改哪一筆。

2.1 Edit 專用的 ViewModel

using System.ComponentModel.DataAnnotations;

namespace MyLeaveSystem.Models.ViewModels;

public class LeaveTypeEditViewModel
{
    // 比 Create 多這一個：要知道在改哪一筆
    public int Id { get; set; }

    [Required(ErrorMessage = "請填寫假別名稱")]
    [StringLength(20)]
    [Display(Name = "假別名稱")]
    public string Name { get; set; } = string.Empty;

    [Required(ErrorMessage = "請填寫代碼")]
    [RegularExpression("^[A-Z_]+$", ErrorMessage = "代碼只能用大寫英文與底線")]
    [Display(Name = "代碼")]
    public string Code { get; set; } = string.Empty;

    [Range(1, 99)]
    [Display(Name = "排序")]
    public int SortOrder { get; set; }

    [StringLength(100)]
    [Display(Name = "說明")]
    public string? Description { get; set; }

    [Display(Name = "啟用")]
    public bool IsActive { get; set; }
}
Id 放在 ViewModel 裡，不是又有 Over-posting 風險嗎？

這次是刻意要收的：使用者確實需要告訴伺服器「我在改第 3 筆」。

但正因為它可以被竄改，POST 端絕對不能只信這個 Id—— 要拿它去資料庫查出真正的那一筆，並且（在有權限概念之後）確認這個人有資格改它。 第 10 章之後你會反覆看到這個檢查。

忘記隱藏的 Id 欄位

這是 Edit 頁最經典的 bug。沒有 <input type="hidden" asp-for="Id" /> 的話， POST 回來時 input.Id 會是 0， 接著 FirstOrDefaultAsync(t => t.Id == 0) 查不到東西， 你就會看到 404 或「找不到資料」。

徵狀是「編輯頁打得開、填完送出卻說找不到」。看到這個徵狀，第一個檢查隱藏欄位。

2.3 POST：更新

修改Controllers/LeaveTypesController.cs
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Edit(LeaveTypeEditViewModel input)
{
    if (!ModelState.IsValid)
    {
        return View(input);
    }

    // ① 一定要重新從資料庫查，不能直接信任送進來的資料
    var entity = await _db.LeaveTypes.FirstOrDefaultAsync(t => t.Id == input.Id);
    if (entity is null)
    {
        return NotFound();
    }

    var code = input.Code.Trim().ToUpperInvariant();

    // ② 代碼不能跟「別人」重複（要排除自己，不然改別的欄位會被自己擋住）
    if (await _db.LeaveTypes.AnyAsync(t => t.Code == code && t.Id != input.Id))
    {
        ModelState.AddModelError(nameof(input.Code), "這個代碼已經被用了");
        return View(input);
    }

    // ③ 逐一寫回。注意：沒有 _db.Update()，也沒有 UPDATE 語句。
    entity.Name        = input.Name.Trim();
    entity.Code        = code;
    entity.SortOrder   = input.SortOrder;
    entity.Description = string.IsNullOrWhiteSpace(input.Description) ? null : input.Description.Trim();
    entity.IsActive    = input.IsActive;

    await _db.SaveChangesAsync();

    TempData["Success"] = $"已更新假別「{entity.Name}」";
    return RedirectToAction(nameof(Index));
}
「代碼重複」檢查要記得排除自己

少了 && t.Id != input.Id 的話，你只是想改個說明、代碼完全沒動， 系統卻會說「這個代碼已經被用了」——因為它查到的就是這筆自己。

這個 bug 在 Create 不會發生（新資料還沒有 Id），只在 Edit 出現，所以特別容易漏。

3. 變更追蹤：為什麼不用寫 UPDATE

上面那段程式碼有個地方很奇怪：你只是改了物件的屬性， 然後呼叫 SaveChangesAsync()，就更新成功了。 沒有 _db.Update(entity)，也沒有任何 SQL。

這叫變更追蹤（Change Tracking）：

  1. 你用 FirstOrDefaultAsync 查出 entity 時， EF Core 就記住了它原本每個欄位的值
  2. 你改了 entity.Name
  3. SaveChangesAsync() 時，它比對「現在的值 vs 記住的值」， 只把真的變了的欄位寫進 UPDATE 語句

把第 6 章第 9 節的 SQL 記錄打開，改一個假別的說明，你會看到：

輸出終端機
Executed DbCommand … [Parameters=[@p0='新的說明' (Size = 100), @p1='3']]
      UPDATE [LeaveTypes] SET [Description] = @p0
      WHERE [Id] = @p1;

只更新了 Description 一欄，其他沒動的欄位完全沒出現。

什麼時候追蹤會失效

如果你查詢時加了 .AsNoTracking()，EF Core 就不會記住原值， 改屬性也不會有任何效果。

所以規則是：只讀不改的查詢加 AsNoTracking()（省記憶體、快一點）， 要改的就不要加。清單頁適合加，Edit 的 GET/POST 不要加。

4. 刪除？還是停用？

真正的 DELETE 很危險。假設有人請過「公假」，然後你把公假這個假別刪掉—— 那些歷史請假單的假別欄位就指向一個不存在的東西了。

軟刪除：用旗標取代真刪除

所以 LeaveType 有 IsActive 這個欄位。 「停用」的意思是：新的請假單不能再選它，但歷史資料完全不受影響。

這在完成品專案是一致的做法：LeaveType.IsActive、 UserAccount.IsActive 都是同樣的用途—— 離職的老師不能刪掉，因為他簽過的單要留紀錄。

4.1 動手：切換啟用狀態

修改Controllers/LeaveTypesController.cs
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> ToggleActive(int id)
{
    var entity = await _db.LeaveTypes.FirstOrDefaultAsync(t => t.Id == id);
    if (entity is null)
    {
        return NotFound();
    }

    entity.IsActive = !entity.IsActive;
    await _db.SaveChangesAsync();

    TempData["Success"] = entity.IsActive
        ? $"已啟用「{entity.Name}」"
        : $"已停用「{entity.Name}」，新的請假單將不會出現此假別";

    return RedirectToAction(nameof(Index));
}
為什麼是 [HttpPost] 而不是 GET？

會改變資料的操作，永遠不要用 GET。

如果做成 <a href="/LeaveTypes/ToggleActive/3">， 那任何人只要騙管理員點一個連結（甚至塞在 <img src="…"> 裡讓他什麼都不用點）， 就能改你的資料。搜尋引擎的爬蟲也會把你整個網站的資料點一輪。

5. 兩個人同時改同一筆

想像這個情境：

  1. A 打開「病假」的編輯頁
  2. B 也打開同一筆的編輯頁
  3. A 把名稱改成「生病假」，儲存
  4. B 把說明改成「需附診斷證明」，儲存

結果：A 的修改被 B 蓋掉了——因為 B 的表單裡帶的還是舊的名稱「病假」。 這叫「後寫入者獲勝」。

本書不處理這個，但你要知道它存在

解法叫「樂觀並行控制」：在 Entity 加一個 [Timestamp] public byte[] RowVersion 欄位， EF Core 會在 UPDATE … WHERE Id = 3 AND RowVersion = 舊值， 對不上就丟 DbUpdateConcurrencyException， 你再提示使用者「這筆資料已被別人修改」。

對這個規模的系統（管理員只有一兩位）風險很低，所以完成品專案也沒做。 但如果你之後要做多人同時編輯的功能，記得回來查這個關鍵字。

6. 四件套完整程式碼

把整個 Controller 對一次，確認你的跟這裡一致：

C#Controllers/LeaveTypesController.cs（本章完成後的樣子）
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Data;
using MyLeaveSystem.Models.Entities;
using MyLeaveSystem.Models.ViewModels;

namespace MyLeaveSystem.Controllers;

public class LeaveTypesController : Controller
{
    private readonly AppDbContext _db;

    public LeaveTypesController(AppDbContext db) => _db = db;

    // ── R：清單 ──
    public async Task<IActionResult> Index()
        => View(await _db.LeaveTypes.AsNoTracking().OrderBy(t => t.SortOrder).ToListAsync());

    // ── C：新增 ──
    [HttpGet]
    public IActionResult Create() => View(new LeaveTypeCreateViewModel());

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Create(LeaveTypeCreateViewModel input)
    {
        if (!ModelState.IsValid) return View(input);

        var code = input.Code.Trim().ToUpperInvariant();
        if (await _db.LeaveTypes.AnyAsync(t => t.Code == code))
        {
            ModelState.AddModelError(nameof(input.Code), "這個代碼已經被用了");
            return View(input);
        }

        _db.LeaveTypes.Add(new LeaveType
        {
            Name = input.Name.Trim(), Code = code, SortOrder = input.SortOrder,
            Description = string.IsNullOrWhiteSpace(input.Description) ? null : input.Description.Trim(),
            IsActive = true
        });
        await _db.SaveChangesAsync();

        TempData["Success"] = $"已新增假別「{input.Name}」";
        return RedirectToAction(nameof(Index));
    }

    // ── U：編輯 ──
    [HttpGet]
    public async Task<IActionResult> Edit(int id)
    {
        var e = await _db.LeaveTypes.FirstOrDefaultAsync(t => t.Id == id);
        if (e is null) return NotFound();

        return View(new LeaveTypeEditViewModel
        {
            Id = e.Id, Name = e.Name, Code = e.Code,
            SortOrder = e.SortOrder, Description = e.Description, IsActive = e.IsActive
        });
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Edit(LeaveTypeEditViewModel input)
    {
        if (!ModelState.IsValid) return View(input);

        var e = await _db.LeaveTypes.FirstOrDefaultAsync(t => t.Id == input.Id);
        if (e is null) return NotFound();

        var code = input.Code.Trim().ToUpperInvariant();
        if (await _db.LeaveTypes.AnyAsync(t => t.Code == code && t.Id != input.Id))
        {
            ModelState.AddModelError(nameof(input.Code), "這個代碼已經被用了");
            return View(input);
        }

        e.Name = input.Name.Trim();
        e.Code = code;
        e.SortOrder = input.SortOrder;
        e.Description = string.IsNullOrWhiteSpace(input.Description) ? null : input.Description.Trim();
        e.IsActive = input.IsActive;
        await _db.SaveChangesAsync();

        TempData["Success"] = $"已更新假別「{e.Name}」";
        return RedirectToAction(nameof(Index));
    }

    // ── D：停用 / 啟用（軟刪除）──
    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> ToggleActive(int id)
    {
        var e = await _db.LeaveTypes.FirstOrDefaultAsync(t => t.Id == id);
        if (e is null) return NotFound();

        e.IsActive = !e.IsActive;
        await _db.SaveChangesAsync();

        TempData["Success"] = e.IsActive ? $"已啟用「{e.Name}」" : $"已停用「{e.Name}」";
        return RedirectToAction(nameof(Index));
    }
}
注意 Index 加了 AsNoTracking() 清單頁只是顯示，不會改任何東西，所以不需要變更追蹤。 加上去之後 EF Core 少建一份快照，資料多的時候差距很明顯。 養成習慣：唯讀查詢一律加。
