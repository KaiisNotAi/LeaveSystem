Flow 03 · Submit Leave Request

學員送出請假單

全系統最長的一條路。一次 POST 裡串了五道業務規則： 時段轉時數 → 班期上限檢查 → 找出對應的簽核規則 → 依規則動態展開 N 關簽核步驟 → 發通知。 每一道不過就 return View(input) 退回表單，全部通過才真正寫進資料庫。

4 _leaveCalculator.TryCalculate(startAt, endAt, out totalHours, out calcError) LeaveRequestsController.cs:118–126 · Services/LeaveCalculator.cs:14

時段 ≠ 時數。上課時段是 08:00–12:00 與 13:00–17:00， 午休 12:00–13:00 不計。LeaveCalculator 用「逐日與兩個上課區段求交集」 的方式計算，所以自然支援跨日。 

// Controller：把日期 + 整點下拉組成 DateTime
var startAt = input.StartDate.Date.AddHours(input.StartHour.Value);
var endAt   = input.EndDate.Date.AddHours(input.EndHour.Value);

if (!_leaveCalculator.TryCalculate(startAt, endAt, out var totalHours, out var calcError))
{
    ModelState.AddModelError(string.Empty, calcError ?? "請假時段計算失敗，請檢查輸入。");
    await PopulateLeaveTypesAsync(input);
    return View(input);
}

// LeaveCalculator.cs：逐日求交集
for (var day = startAt.Date; day <= endAt.Date; day = day.AddDays(1))
{
    totalHours += OverlapHours(requestRange, (day.AddHours(8),  day.AddHours(12)));  // 上午
    totalHours += OverlapHours(requestRange, (day.AddHours(13), day.AddHours(17)));  // 下午
}
為什麼用 TryCalculate 而不是丟例外
「使用者填錯時段」是預期內的情況，不是程式錯誤。 bool + out errorMessage 的形式讓 Controller 可以直接把訊息塞回 ModelState 顯示給使用者，不必寫 try/catch。
5 SumAsync(r => r.TotalHours) 與 Cohort.LeaveLimitHours 比較 LeaveRequestsController.cs:128–141

統計口徑：只累計 Status == Approved。 還在簽核中的單不算，所以理論上可能同時送出多張、全部核准後才超標—— 這是刻意的取捨（見下方設計決策）。 LeaveLimitHours 是 Cohort 上的計算屬性： TotalHours × LeaveLimitPercent / 100 無條件捨去。 

var approvedHours = await _db.LeaveRequests

6 _db.ApprovalRules.OrderBy(MinHours).FirstOrDefaultAsync(區間比對) LeaveRequestsController.cs:143–155

簽核層級不是寫死在程式裡的。 它是查 ApprovalRules 資料表，找出 MinHours ≤ 時數 ≤ MaxHours 的那一條。 MaxHours 為 null 代表「無上限」，對應最高那一級。 Admin 在 /Admin/ApprovalRules 改門檻，不用改程式、不用重啟就生效。 

var matchedRule = await _db.ApprovalRules
    .OrderBy(r => r.MinHours)
    .FirstOrDefaultAsync(r =>
        r.MinHours <= totalHours &&
        (!r.MaxHours.HasValue || totalHours <= r.MaxHours.Value));

10 await _notifications.NotifySubmittedAsync(leaveRequest.Id) LeaveRequestsController.cs:193

順序很重要：一定在 SaveChangesAsync() 之後。 通知只傳 leaveRequest.Id，而 Id 是資料庫在存檔那一刻才產生的； 存檔前呼叫會傳出 0，通知內容跟連結全都會是錯的。 後續怎麼找到「這一關該通知誰」，見 05 通知流程。 

await _db.SaveChangesAsync();

await _notifications.NotifySubmittedAsync(leaveRequest.Id);   // ← Id 這時候才有值

關鍵設計決策

決策為什麼
簽核層級查表而非寫死 機構的簽核門檻會改（例如把 8 小時改成 4 小時）。 做成 ApprovalRules 資料表後，Admin 自己改，程式不用動。
送單時不決定「誰簽」，只決定「哪個角色簽」 若送單當下就把導師的 UserId 寫死進 Step，之後班期換導師， 舊的單就會卡在離職的人身上。改成簽核當下再查 Cohort.TutorUserId，換人立即生效。
上限只算已核准時數 若把 Pending 也算進去，學員送了單又被駁回，額度會被莫名其妙佔住。 代價是同時送多張、事後全核准有機會超標——實務上由簽核人把關。
整點下拉而非自由輸入時間 LeaveCalculator 最小單位是 1 小時。 前端限制 08~17 整點，IsOnTheHour / IsSelectableHour 在伺服器端再擋一次，避免有人繞過前端直接送。

  4. 把第 10 步的 NotifySubmittedAsync 搬到 SaveChangesAsync() 之前， 觀察通知連結變成 /Approvals/Details/0。看過就改回來。
