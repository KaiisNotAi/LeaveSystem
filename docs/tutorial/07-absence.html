曠課紀錄 CRUD 與雙 Controller 分流

曠課跟請假完全不同：請假是事前申請、要走簽核； 曠課是事後行政登錄的既成事實，沒有簽核流程。 程式上最有趣的地方是：專案裡存在兩個同名的 AbsenceRecordsController， 一個給學員自查、一個給行政管理，靠路由與 View 路徑分流。

陷阱：兩個 Controller 名字一樣，Razor 會找錯 View
Razor 預設用 Controller 名稱（不含命名空間）去 Views/{ControllerName}/ 找 View。 兩個都叫 AbsenceRecords，所以行政端的 return View(vm) 會跑去載入學員端的 Views/AbsenceRecords/Index.cshtml， 然後因為 ViewModel 型別不合而爆掉。
解法：在 Program.cs 多插一條 View 搜尋路徑
01 啟動流程第 2 步那段 （Program.cs:27）把 /Views/Admin/{1}/{0}.cshtml 插到搜尋清單的最前面，Admin 版就會優先命中 Views/Admin/AbsenceRecords/。更完整的討論見 10-曠課紀錄教學.md §4。

5 CheckStudentAsync(input.StudentId) Services/AbsenceRecordService.cs:48–52, 267–285

兩層規則合成一個方法：這個 UserId 必須 ① 存在且擁有 Student 角色、② 已指派班期。 回傳型別是 string?——有錯誤訊息代表失敗，null 代表通過， 呼叫端可以直接把它塞進 ActionResult，不必自己判斷是哪一條規則沒過。 

private async Task<string?> CheckStudentAsync(int userId)
{
    var info = await _db.UserAccounts
        .AsNoTracking()
        .Where(u => u.Id == userId
            && u.UserRoles.Any(ur => ur.Role.Name == RoleNameStudent))
        .Select(u => new { u.CohortId })      // 只取需要的欄位
        .FirstOrDefaultAsync();

    if (info is null)         return ErrorStudentNotFound;
    if (info.CohortId is null) return ErrorStudentNoCohort;
    return null;   // null = 通過
}
為什麼要求「必須有班期」
行政清單與匯出報表都以班期為主要篩選維度。 沒班期的學員登錄了曠課，會變成查不到也匯不出的孤兒資料。
6 NormalizeNote(input.Note) Services/AbsenceRecordService.cs:239–243

使用者在備註欄按了幾個空白就送出，得到的是 " " 而不是 null。 正規化成 null 之後，View 的 @(record.Note ?? "—") 才會正確顯示破折號， 查詢時也不會出現「看起來空白但 IS NOT NULL」的資料。 

private static string? NormalizeNote(string? note)
{
    if (string.IsNullOrWhiteSpace(note)) return null;
    return note.Trim();
}
7 _db.AbsenceRecords.Add(record); await _db.SaveChangesAsync(); Services/AbsenceRecordService.cs:54–67

CreatedByUserId 與 CreatedAt 是稽核欄位， 只在 CreateAsync 寫入一次。 對照 UpdateAsync（:85–89）—— 它刻意不碰這兩個欄位： 

// CreateAsync：稽核欄位在這裡寫入
var record = new AbsenceRecord
{
    StudentId = input.StudentId, OccurredAt = input.OccurredAt,
    Hours = input.Hours, Note = NormalizeNote(input.Note),
    CreatedByUserId = createdByUserId,   // ← 只有這裡寫
    CreatedAt = DateTime.UtcNow          // ← 只有這裡寫
};

// UpdateAsync：只更新業務欄位
// 更新業務欄位；CreatedByUserId 與 CreatedAt 刻意保留，維持原稽核資訊
record.StudentId  = input.StudentId;
record.OccurredAt = input.OccurredAt;
record.Hours      = input.Hours;
record.Note       = NormalizeNote(input.Note);
為什麼 Update 不能覆寫稽核欄位
若 UpdateAsync 也寫 CreatedByUserId = 目前使用者， 那 A 建立、B 只改了一個錯字，紀錄就會變成「B 建立的」。 稽核資訊的意義是「這筆資料最初是誰、什麼時候放進來的」，一旦被覆寫就失去價值。
8 record AbsenceRecordActionResult(bool Success, string? ErrorMessage, int? RecordId = null) Services/IAbsenceRecordService.cs:117

跟 04 簽核的 ApprovalActionResult 是同一個體例： Service 不丟例外、不直接回 IActionResult， 只回一個描述結果的 record。所有錯誤訊息都是 Service 裡的常數， 測試才驗得到、Controller 也不用自己編字串。

9 成功 → RedirectToAction(nameof(Index))；失敗 → View(input) Controllers/Admin/AbsenceRecordsController.cs:83–94

跟送單一樣採 POST-Redirect-GET。失敗時記得再次重填下拉—— 這是這個 Action 裡出現兩次的同一段程式碼（第 2 步一次、這裡一次；Edit 也有兩份）。 錯誤訊息掛在 nameof(input.StudentId) 而不是 string.Empty， 這樣訊息會直接顯示在學員下拉旁邊，而不是表單最上方的摘要區。

另一個容易踩的坑：日期迄的「含當天」語意

<input type="date"> 只帶日期，繫結成 DateTime 時間部分是 00:00:00。 若直接拿去比 OccurredAt <= dateTo， 6/30 晚上 20:00 那筆就查不到——因為 20:00 > 00:00。 

// AbsenceRecordService.cs:250–255
private static DateTime NormalizeDateTo(DateTime dateTo)
{
    return dateTo.TimeOfDay == TimeSpan.Zero
        ? dateTo.Date.AddDays(1).AddTicks(-1)   // 補到當日 23:59:59.9999999
        : dateTo;                               // 使用者自己給了時間就照用
}

LeaveReportService.GetAdminReportAsync 用的是同一套體例，兩邊的日期語意才會一致。
