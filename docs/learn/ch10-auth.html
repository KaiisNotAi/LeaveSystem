1. 密碼絕對不能存明碼

資料庫總有一天會外洩（被駭、備份檔放錯地方、離職員工帶走）。 如果裡面是明碼密碼，災難不只在你的網站—— 很多人到處用同一組密碼。

做法安全嗎
直接存密碼❌ 外洩＝全滅
MD5 / SHA1 / SHA256 ❌ 太快了。現代顯示卡一秒可以試幾十億組，常見密碼幾秒就破
BCrypt（本書用） ✅ 刻意設計成很慢，而且每次加不同的隨機鹽
「慢」為什麼是優點？

使用者登入一次，慢 0.2 秒完全無感。 但攻擊者要暴力破解，就從「一秒試十億組」變成「一秒試五組」—— 差距是幾億倍。

另外 BCrypt 會自動加一段隨機的「鹽」，所以同樣的密碼每次算出來的雜湊都不一樣。 攻擊者沒辦法用預先算好的對照表（彩虹表）一次破解一堆帳號。

終端機安裝 BCrypt
dotnet add package BCrypt.Net-Next

新增檔案Services/BcryptPasswordHasher.cs
namespace MyLeaveSystem.Services;

public class BcryptPasswordHasher : IPasswordHasher
{
    public string Hash(string password)
        => BCrypt.Net.BCrypt.HashPassword(password);

    public bool Verify(string password, string hash)
    {
        try
        {
            return BCrypt.Net.BCrypt.Verify(password, hash);
        }
        catch
        {
            // 資料庫裡的雜湊格式壞掉時不要整個爆掉，當成驗證失敗
            return false;
        }
    }
}
包成介面的另一個好處 BCrypt 每次驗證要花約 0.2 秒。第 9 章那種測試如果要跑幾百次， 就會慢到不能忍。包成介面之後，測試可以塞一個「直接比對字串」的假實作。

2. AuthService

登入其實是兩件獨立的事： 驗證（你是不是你）與簽入（把身分寫成 Cookie）。

新增檔案Services/IAuthService.cs
using MyLeaveSystem.Models.Entities;

namespace MyLeaveSystem.Services;

public interface IAuthService
{
    /// 驗證帳密。成功回使用者（含角色），失敗回 null。
    Task<UserAccount?> ValidateAsync(string username, string password);

    /// 寫入 Cookie 完成登入。
    Task SignInAsync(HttpContext context, UserAccount user, bool isPersistent = false);

    /// 清除 Cookie 完成登出。
    Task SignOutAsync(HttpContext context);
}
新增檔案Services/AuthService.cs
using System.Security.Claims;
using Microsoft.AspNetCore.Authentication;
using Microsoft.AspNetCore.Authentication.Cookies;
using Microsoft.EntityFrameworkCore;
using MyLeaveSystem.Data;
using MyLeaveSystem.Models.Entities;

namespace MyLeaveSystem.Services;

public class AuthService : IAuthService
{
    private readonly AppDbContext _db;
    private readonly IPasswordHasher _passwordHasher;

    public AuthService(AppDbContext db, IPasswordHasher passwordHasher)
    {
        _db = db;
        _passwordHasher = passwordHasher;
    }

    public async Task<UserAccount?> ValidateAsync(string username, string password)
    {
        // 連角色一起載入 —— 下一步 SignInAsync 馬上要用（避免查兩次）
        var user = await _db.UserAccounts
            .Include(u => u.UserRoles)
                .ThenInclude(ur => ur.Role)
            .FirstOrDefaultAsync(u => u.Username == username);

        if (user is null) return null;                                    // 查無帳號
        if (!user.IsActive) return null;                                  // 已停用
        if (!_passwordHasher.Verify(password, user.PasswordHash)) return null;  // 密碼錯

        return user;
    }

    public async Task SignInAsync(HttpContext context, UserAccount user, bool isPersistent = false)
    {
        // 一筆 Claim = 一個「身分屬性」
        var claims = new List<Claim>
        {
            new(ClaimTypes.NameIdentifier, user.Id.ToString()),   // ← 第 6 節會一直用到
            new(ClaimTypes.Name, user.DisplayName),
            new("Username", user.Username)
        };

        // 每個角色加一筆。[Authorize(Roles="Admin")] 比對的就是這些。
        foreach (var ur in user.UserRoles)
        {
            if (ur.Role is not null)
                claims.Add(new Claim(ClaimTypes.Role, ur.Role.Name));
        }

        var identity  = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
        var principal = new ClaimsPrincipal(identity);

        var properties = new AuthenticationProperties
        {
            IsPersistent = isPersistent,                      // 勾「記住我」才持久化
            ExpiresUtc   = DateTimeOffset.UtcNow.AddHours(8)
        };

        // 這一行才真的寫出 Set-Cookie
        await context.SignInAsync(
            CookieAuthenticationDefaults.AuthenticationScheme, principal, properties);
    }

    public Task SignOutAsync(HttpContext context)
        => context.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
}
為什麼三種失敗都回同一個 null？

如果分別回「查無此帳號」與「密碼錯誤」，攻擊者就能用它來列舉出哪些帳號存在， 再集中火力猜那些帳號的密碼。

所以畫面上一律顯示「帳號或密碼錯誤，或帳號已停用」—— 使用者稍微不方便，但安全性差很多。

Claim 是什麼

就是一組「鍵 = 值」的身分描述。 NameIdentifier = "5"、Role = "Tutor"、Role = "Staff"。

它們會被加密簽章後放進 Cookie。 使用者可以看到那串亂碼，但改不動—— 改了簽章就對不上，伺服器會當成未登入。

3. 設定 Cookie 認證

修改Program.cs
using Microsoft.AspNetCore.Authentication.Cookies;

builder.Services.AddScoped<ILeaveCalculator, LeaveCalculator>();
builder.Services.AddScoped<IPasswordHasher, BcryptPasswordHasher>();
builder.Services.AddScoped<IAuthService, AuthService>();

builder.Services
    .AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.LoginPath        = "/Account/Login";         // 未登入 → 轉這裡
        options.AccessDeniedPath = "/Account/AccessDenied";  // 角色不足 → 轉這裡
        options.ExpireTimeSpan   = TimeSpan.FromHours(8);
        options.SlidingExpiration = true;                    // 使用中會自動延長
        options.Cookie.Name      = "MyLeaveSystem.Auth";
        options.Cookie.HttpOnly  = true;                     // JS 讀不到，降低 XSS 風險
    });

然後是本章最容易寫錯的一行——在管線裡加入 UseAuthentication()：

修改Program.cs（Build 之後的下半段）
app.UseRouting();

app.UseAuthentication();   // ← 一定要在 UseAuthorization 之前！
app.UseAuthorization();
順序寫反不會有編譯錯誤

UseAuthentication 負責「你是誰」（解開 Cookie 還原身分）， UseAuthorization 負責「你能不能」。 先算出你是誰，才判斷得了你能不能。

順序反了的話，授權階段拿到的 User 永遠是匿名的， 所有掛 [Authorize] 的頁面都會變成永遠拒絕， 而且程式跑得起來、完全不報錯。

這是 ASP.NET Core 新手第一名的坑。 回頭看第 2 章第 5 節， 管線順序的重要性就是在講這件事。

4. 動手：登入頁

4.1 給預設管理員一個真的密碼

第 8 章的種子資料把 PasswordHash 填成假字串，現在補上：

修改Data/SeedData.cs
public const string DefaultAdminUsername = "Admin";
public const string DefaultAdminPassword = "Admin@123";

private static void SeedAdminUser(AppDbContext db)
{
    if (db.UserAccounts.Any(u => u.Username == DefaultAdminUsername)) return;

    var admin = new UserAccount
    {
        Username     = DefaultAdminUsername,
        DisplayName  = "系統管理員",
        // 種子資料裡直接呼叫 BCrypt（這裡沒有 DI 可用）
        PasswordHash = BCrypt.Net.BCrypt.HashPassword(DefaultAdminPassword),
        IsActive     = true
    };
    db.UserAccounts.Add(admin);
    db.SaveChanges();

    var adminRole = db.Roles.First(r => r.Name == "Admin");
    db.UserRoles.Add(new UserRole { UserId = admin.Id, RoleId = adminRole.Id });
    db.SaveChanges();
}

記得在 Initialize 裡呼叫它（放在 SeedRoles 之後）， 並把第 8 章那兩位示範使用者的 PasswordHash 也改成 BCrypt.Net.BCrypt.HashPassword("Demo@123")。 然後刪掉資料庫重新啟動。

新增檔案Controllers/AccountController.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using MyLeaveSystem.Models.ViewModels;
using MyLeaveSystem.Services;

namespace MyLeaveSystem.Controllers;

// 整個 Controller 開放未登入存取（不然沒人進得來登入頁）
[AllowAnonymous]
public class AccountController : Controller
{
    private readonly IAuthService _authService;
    public AccountController(IAuthService authService) => _authService = authService;

    [HttpGet]
    public IActionResult Login(string? returnUrl = null)
        => View(new LoginViewModel { ReturnUrl = returnUrl });

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Login(LoginViewModel input)
    {
        // ① 欄位有沒有填
        if (!ModelState.IsValid) return View(input);

        // ② 帳密對不對
        var user = await _authService.ValidateAsync(input.Username, input.Password);
        if (user is null)
        {
            ModelState.AddModelError(string.Empty, "帳號或密碼錯誤，或帳號已停用");
            return View(input);
        }

        // ③ 寫 Cookie
        await _authService.SignInAsync(HttpContext, user, input.RememberMe);

        // ④ 導回原本想去的頁面
        if (!string.IsNullOrEmpty(input.ReturnUrl) && Url.IsLocalUrl(input.ReturnUrl))
            return Redirect(input.ReturnUrl);

        return RedirectToAction("Index", "Home");
    }

    // 登出用 POST，不用 GET
    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Logout()
    {
        await _authService.SignOutAsync(HttpContext);
        return RedirectToAction("Index", "Home");
    }

    [HttpGet]
    public IActionResult AccessDenied() => View();
}
Url.IsLocalUrl 這個檢查不能省：Open Redirect

沒有它的話，攻擊者可以散布這種連結：
https://你的網站/Account/Login?returnUrl=https://假冒的登入頁

使用者看到的是你的網域、登入也是真的成功， 但登入後被送到攻擊者的網站，那裡再假裝「登入逾時請重新登入」騙一次密碼。 IsLocalUrl 確保只能轉到自己站內。

登出為什麼一定要 POST 如果做成 GET，攻擊者只要在論壇貼一張 <img src="https://你的網站/Account/Logout">， 所有看到那則貼文的人都會被登出。雖然只是騷擾，但完全沒必要留這個洞。

6. 最重要的一課：只能看自己的資料

[Authorize(Roles = "Student")] 只擋掉「不是學員的人」。 它擋不住「學員 A 去看學員 B 的資料」。

C#❌ 有嚴重漏洞的寫法
[Authorize(Roles = "Student")]
public async Task<IActionResult> MyRequests(int studentId)
{
    // 💥 studentId 是網址上帶來的，任何學員都能改成別人的 Id
    var list = await _db.LeaveRequests
        .Where(r => r.StudentId == studentId)
        .ToListAsync();

    return View(list);
}

/LeaveRequests/MyRequests?studentId=7 —— 改個數字就看到別人的請假紀錄了。

C#✅ 正確做法：身分只從 Cookie 取
[Authorize(Roles = "Student")]
public async Task<IActionResult> MyRequests()      // ← 沒有參數
{
    var studentId = GetCurrentUserId();
    if (studentId is null) return Forbid();

    var list = await _db.LeaveRequests
        .Where(r => r.StudentId == studentId.Value)
        .ToListAsync();

    return View(list);
}

把取得目前使用者 Id 的方法寫成共用的基底類別：

新增檔案Controllers/AppControllerBase.cs
using System.Security.Claims;
using Microsoft.AspNetCore.Mvc;

namespace MyLeaveSystem.Controllers;

public abstract class AppControllerBase : Controller
{
    /// 從 Cookie 的 Claim 取得目前登入者的 Id。
    /// 這個值使用者「改不動」，因為 Cookie 有簽章。
    protected int? GetCurrentUserId()
    {
        var raw = User.FindFirstValue(ClaimTypes.NameIdentifier);
        return int.TryParse(raw, out var id) ? id : null;
    }
}

之後你的 Controller 就繼承它：public class ReportsController : AppControllerBase。

記住這條規則，它會救你很多次

「我是誰」永遠從 Cookie 取，絕對不要從網址、表單或任何使用者可以改的地方取。

這類漏洞有個名字叫 IDOR（不安全的直接物件參考）， 是實務上最常見的資安問題之一—— 因為它功能完全正常，測試也測不出來，只有攻擊者會發現。

涉及「別人的資料」的每一個 Action，都要問自己： 這個 id 是誰給的？我有沒有確認這個人有權限碰它？

藏起來 ≠ 擋住

把選單藏起來只是介面上的體貼。 使用者還是可以自己在網址列打 /Users。

真正的防線永遠是 Controller 上的 [Authorize]。 View 的 @if 只是不要讓使用者看到自己按了會被拒絕的按鈕。 兩個都要做，但只有一個是安全機制。

改了角色要重新登入才生效 因為角色是登入當下寫進 Cookie 的快照。 在 /Users 把某人改成 Admin，他要登出再登入才會拿到新角色。 這是「用 Cookie 存角色」換來效能的代價（每個請求不用再查一次資料庫）。
